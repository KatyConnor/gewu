# LPU 规则 · 10 重构建议阶段（S5 · RBH）

> 重构建议回答：基于以上全部理解，这个项目应该怎么重生。
> Agent 的产出是"建议"（供人决策），不是"决定"。每条建议必须标注依据与风险。

---

### LPU-RBH-001【M】重构策略四选一评估
必须评估并给出推荐（依据 + 反对理由也要写）：

| 策略 | 适用信号 | 主要风险 |
|---|---|---|
| 绞杀者模式（Strangler Fig） | 系统仍在服役、功能可渐进迁移 | 双轨期数据一致性成本 |
| 就地重构 | 架构尚可、技术债集中在局部 | 改动波及面失控 |
| 平台重建（重写） | 技术栈彻底过时、文档本包已还原业务全景 | 隐式规则丢失（对照 DIV-K-003 清单逐条防御） |
| 冻结维持 | 业务即将下线/替换中 | 机会成本 |

评估输入：debt-risks 的债务总量与分布、业务规则密度、测试覆盖画像、死代码占比、团队约束（若用户告知）。

### LPU-RBH-002【M】迁移边界与顺序建议
- 依据依赖图（SKL-002）划定迁移单元：优先迁移**被依赖少、入口清晰**的模块（低风险试点）；
- 每个迁移单元给出：包含范围（模块+表+API 清单）、依赖前置、验证方式（依据现状行为写验收标准）；
- 状态字段与枚举映射方案（旧值→新值）必须逐条列出，禁止"迁移时再定"。

### LPU-RBH-003【M】风险登记
每条建议附带风险登记（至少覆盖）：
- 隐式规则丢失风险：引用 DIV-K-003 清单逐条对照，标注"已防御/未防御"；
- 数据迁移风险：引用 DIV-D-006 脏数据清单；
- 集成中断风险：引用 DIV-C-006 集成点清单；
- 灰度与回滚可行性：依据状态机与双写可行性给出初步判断。

### LPU-RBH-004【R】价值锚定的优先级
建议排序按"风险消除价值"而非"技术洁癖"：先解决"高频事故区"（吞异常+资金计算+集成超时），
再处理"开发效率区"（死代码/复制粘贴族），最后"体验优化区"。每项标注预估收益等级（高/中/低）。

### LPU-RBH-005【M】待人工确认清单（最终交付）
汇总全流程的 C 级结论与 X4 级冲突，逐条输出：
`编号 / 问题 / 证据 / 建议确认方式（问谁/查什么）/ 对重构方案的影响（若确认结果为 X 则…）`。
**这份清单是 LPU 交付物中人工参与的唯一必经入口**——它的质量决定整个分析的可信上限。

### LPU-RBH-006【O】重构后文档维护建议
给出重构期文档同步机制建议（如：新代码 PR 必须同步更新 features-api.md 对应条目），
避免新系统再次退化为"无文档遗留项目"。
