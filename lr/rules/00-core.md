# LR 核心 · 00-core（LR-STD-001 V1.0）

> 遗留项目重构工程规范核心规则。本文件与 LPU-STD-001（逆向理解）前后接力：
> LPU 回答"这个系统是什么、值不值得重构、怎么分块"，LR 回答"如何把重构安全落地"。

## 0. 定位与边界

**你（Agent）此刻所处的位置**：LPU 已完成（`docs/lpu/` 8 份文档齐备，
`rebuild-plan.md` 给出了策略与迁移单元建议），用户决定实施重构。
LR 管理从"决策立项"到"旧系统退役归档"的完整工程。

| 规范 | 分界 |
|---|---|
| LPU-STD-001 | 理解与建议（只读分析，到 rebuild-plan 为止） |
| **LR-STD-001（本规范）** | **重构实施（从立项决议到退役归档）** |
| SDLC-SKILLS | 单元内的常规开发角色能力（LR 在 R4 引用，不重复定义） |
| CR-RULES | 新代码质量门（R1 采纳、R4/R5 执行） |
| AETC-STD-001 | 全程留痕（LR 的 R2/R3 级操作走其 GATE 审批） |

## 1. 五条铁律（任何情况下不可违反）

1. **无基线，不重构**：R3 防护网（行为基线测试 + 数据快照 + 回滚预案）未通过门禁前，
   禁止修改任何旧系统代码、禁止切换任何流量。
2. **无文档，不推进**：每个阶段出口有必输文档清单（Doc-Gate），文档不齐不得进入下一阶段；
   文档可以迭代完善，但不可以缺席。
3. **小步快走**：按迁移单元增量交付，一次只切换一个单元；禁止大爆炸式整体替换
   （Big-Bang Rewrite 是被本规范禁止的默认项，除非立项决议书中有专项豁免论证）。
4. **行为等价优先**：每个单元切换前必须完成新旧对照验证（相同输入→行为一致），
   未取得一致性证明的单元不得切换；有意改变的行为必须显式登记为"行为变更项"并经确认。
5. **全程留痕**：与 AETC 协同——阶段切换、批量修改、数据迁移、流量切换均为 R2/R3 级操作，
   先 GATE_REQUEST 获批、留检查点，再动手。

## 2. 七阶段总览（R0~R6）

| 阶段 | 名称 | 核心动作 | 必输文档 |
|---|---|---|---|
| R0 | 决策与立项 | 策略确认/范围圈定/审批链 | D-R0-01 立项决议书 · D-R0-02 准入核查单 |
| R1 | 目标与规范 | 目标架构/选型ADR/工程规范/数据模型 | D-R1-01~04 |
| R2 | 规划与拆解 | 迁移单元细化/路线图/风险登记 | D-R2-01~03 |
| R3 | 基线与防护网 | 特征测试/金样本/数据快照/回滚预案 | D-R3-01~03 |
| R4 | 增量实施 | 逐单元绞杀者循环（方案→实施→对照→切换→观察） | D-R4-01 日志 · D-R4-02 追溯矩阵 + 每单元三件套 |
| R5 | 验收与切换 | 全量验收/数据终验/退役归档 | D-R5-01~03 |
| R6 | 复盘与沉淀 | 复盘六问/文档总目录/知识库更新 | D-R6-01~02 |

阶段规则详见 `lr/rules/01~07-*.md`；文档模板契约见 `lr/templates/`（22 份）。

## 3. 文档门禁机制（Doc-Gate）

- **出口条件**：阶段必输文档全部 approved + `lr_check.py` 对应范围 PASS。
- **状态机**：pending → drafting → review → approved；任一必输文档回退为 draft，
  当前阶段门禁自动降级为不通过（复检规则）。
- **单元级门禁**（R4 内部）：方案 → 实施 → 对照验证 → 切换（AETC R3 级 GATE）→ 观察期。
  观察期超阈值 → 按回滚预案执行，单元回炉重新对照。
- **校验工具**：`python3 lr/scripts/lr_check.py --stage R0..R6`（或 `--all`），
  报告落位 `.lr/lr-check-report.md`，G1~G8 分组见 scripts 内文档头。

## 4. 触发与续跑

**进入 LR 的条件**（满足其一）：
1. `docs/lpu/rebuild-plan.md` 存在，且用户表达实施意图（重构实施/开始重构/落地重构/
   迁移改造/系统改造/绞杀者改造/退役旧系统）；
2. 项目根存在 `.lr/` 工作目录（续跑模式：读 `.lr/progress/PROGRESS.md` 恢复现场）；
3. 用户直接指令"执行 LR / 重构工程"。

**前置核查**：`docs/lpu/` 8 份文档齐备是 R0 立项的硬前置；不齐时先回 LPU 补齐
（本规范不放松 LPU 的产出要求）。

**初始化**：首次进入时将 `lr/init/` 复制为 `.lr/`（config.json + progress/），
随后从 R0 开始。

## 5. 与 AETC 的操作分级协同

| LR 动作 | AETC 风险级 | 管控 |
|---|---|---|
| 编写/更新 D-xx 文档 | R1 | 留痕+事后抽审 |
| 新系统代码编写（新建文件） | R1 | 留痕；CR 质量门 |
| 修改旧系统代码（双轨期修补） | R2 | GATE 事前确认+检查点 |
| 数据迁移脚本执行 | R2 | GATE+检查点+数据快照 |
| 流量切换/单元上线 | R3 | 强制审批+回滚预案就绪（D-R3-03 引用） |
| 旧系统下线/归档删除 | R3 | 强制审批+归档副本先行 |

## 6. Agent 行为规范

- 进入任一阶段前，先读本规则与该阶段规则文件（`lr/rules/01~07`）。
- 每完成一份必输文档，立即更新 `.lr/progress/PROGRESS.md` 并运行 `lr_check.py`。
- 阶段规则与用户指令冲突时：安全类条款（铁律 1/4/5）不得让步，
  流程类条款可经用户显式豁免并记录于立项决议书。
- 所有"待人工确认清单"（源自 LPU rebuild-plan 与本规范新增）必须逐条闭环，
  闭环记录写入对应 D-xx 文档的确认章节。
