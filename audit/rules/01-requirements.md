# S1 需求分析阶段规则（01-requirements.md）

阶段目标：把模糊需求转化为可验证、可追溯的需求基线（PRD/用户故事/验收标准）。
phase 值：requirements

## Agent 职责边界
- 应做：需求澄清提问、领域资料调研、竞品/技术约束分析、PRD 草案撰写、验收标准清单、影响面初判。
- 禁止：代替业务方拍板需求范围；在需求未确认（G1 未过）前进入设计或编码；
  将未澄清的假设写入需求而不标注。

## 必检点（进入下一阶段前逐项确认）
1. 任务目标一句话复述，且与发起人意图一致。
2. 显式约束（性能/合规/兼容/预算/期限）已逐条列出。
3. 每条假设已标注 ASSUMPTION 并列入待确认问题清单。
4. 验收标准可测试（有可执行/可核验的判定方式）。
5. 影响面清单（涉及模块、数据、接口、第三方）已完成初判。

## 留痕要求
- TASK_OPEN：完整记录任务描述与初始理解。
- DECISION：需求取舍点（范围裁剪、优先级排序）必须记录备选与理由。
- STEP_DONE：调研类步骤合并记录，列出资料清单。
- PLAN_COMMIT：进入 S2 前提交整体计划。

## 审批门 G1（需求确认）
- 请求时机：PRD 草案完成、必检点全绿。
- GATE_REQUEST 内容：PRD 路径、验收标准摘要、假设清单、待确认问题。
- 通过标准：发起人明确批准（approved/modified）；未决问题不允许超过 0 个关键级 + 2 个一般级。

## 常见风险与回退
- 需求理解偏差：G1 之前发现的，直接 CORRECTION 修订草案；G1 之后发现的，
  走变更流程（新的 GATE_REQUEST + 受影响分析）。
- 需求基线文件纳入版本控制，回退即恢复 PRD 检查点版本。
