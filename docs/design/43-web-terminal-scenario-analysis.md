## 0. 结论先行

**有实际使用意义，但价值分层明显**：对"文档批量处理 + 开发验证"两类场景价值真实且高（★★★）；对纯阅读型文档用户价值有限。决定投入产出的关键不是"做不做终端"，而是两个选择：**形态**（命令循环 vs 完整 PTY）与**工具链**（镜像要不要扩展）。

既有基础比预想好——命令循环形态的终端在开发空间页**已经存在**，exec 通道、危险命令扫描、资源限额、审计全部现成，MVP 边际成本很低。

## 3. 业界参照

| 产品 | 形态 | 验证点 |
|---|---|---|
| 阿里云 Cloud Shell / AWS CloudShell | 挂载持久存储的网页终端 | "终端+持久工作区"是被广泛接受的独立价值 |
| Google Colab / JupyterHub | 代码单元+持久运行时 | 数据处理场景高频 |
| ChatGPT Code Interpreter / Claude 分析工具 | AI 代跑（一次性沙箱） | 与本平台 code_execute 同型——证明 AI 代跑覆盖"单次命令"场景 |
| Cursor / Claude Code | AI 代理 + 本地终端并存 | 证明"AI 生成 + 人终端验证"回路的必要性 |

差异化定位：本平台若做终端，独特价值在 **S9 回路**——AI、终端、"我的文件"三方共享同一持久卷，这是纯终端产品与纯 AI 产品都不具备的组合。

## 4. 价值论证

### 正方
1. **确定性**：AI 执行有失败率与 token 成本，终端零成本且结果可靠
2. **批量效率**：100 个文件的重命名/转换，对话式逐个操作不现实
3. **即时反馈**：开发者的直接操作路径，无需组织自然语言
4. **兜底价值**：AI 链路故障时用户仍能自助处理文件
5. **平台协同**：与同步服务组合后，卷成为 AI/终端/"我的文件"三方协作中枢

### 反方（必须正视）
1. 与 AI `code_execute` 能力重叠度高——"让 AI 帮你跑"覆盖大部分单次命令场景
2. 开发空间页已有简易终端，同一用户两个终端入口需收敛（MVP 应明确二合一或分置策略）
3. 安全面扩大：网络开启 + rootfs 可写，用户可装任意软件（容器内风险可控，但镜像漂移、资源滥用需治理）
4. 若目标用户以文档协作为主，使用频率可能很低

### 判定变量
**平台主力用户画像**。开发者占比高 → S7/S9 权重高，值得做；纯文档用户为主 → 只做 S1/S2（甚至用普通 API 实现打包下载而无需终端）。

## 5. 技术形态选择

| | 形态 A：命令循环终端 | 形态 B：完整 PTY 终端 |
|---|---|---|
| 体验 | 输入→执行→追加输出（开发空间现状同款）；cd 不保持、无 vim/交互程序 | xterm.js + WebSocket + docker exec TTY attach；完整交互体验 |
| 后端改动 | **零**（/exec 通道现成） | gewu-sandbox 新增 WS 端点 + PTY 会话管理 + 心跳/断连恢复 |
| 前端改动 | 复用开发空间终端组件搬入"我的文件" | xterm.js + attach addon |
| 成本 | **2~3 人日** | **5~8 人日** |
| 建议 | **MVP 首选**——S1/S2/S5/S7/S9 均不需要 PTY | 二期按需 |

**前置动作**：`启动沙箱` 按钮收编为 dev 沙箱启动器（42 号文档讨论的路线 B）——按钮调 `ensureDevSandboxForUser`（探活/惰性创建），显示运行状态；终端做在 dev 沙箱上，坚持"一用户一沙箱"原则，不再新建 source=workspace 容器。

## 6. 安全与治理清单

已在位：危险命令扫描（CodeScanner 前置）✓、执行超时熔断 ✓、CPU/内存/Pid 限额 ✓、exec 审计 ✓、网络独立开关（dev 可单独关闭）✓、每用户独立卷（rm -rf 只伤自己）✓。

需补决策：镜像工具链固化策略——apt 安装随容器销毁，要么写入 `Dockerfile.dev` 重新出镜像（S3 需要此路径），要么在产品层面明确"终端为临时环境"的用户心智。
