## 一、背景与方向裁定

### 1.1 决策演进脉络

| 时间 | 文档 | 决策 | 状态 |
|---|---|---|---|
| 2026-07 | 29 号 ADR-001 | "统一编排模型消双轨"——工作流引擎降级为图执行器后端 | 未兑现（工作流模块保留） |
| 2026-08-27 | 28 号 V1.2 | "两轨保留、不再合并"：工作流=人工审批流，编排=Agent DAG | 沿用至今 |
| 2026-09-25 | 48 号 | 编排先行；**BPM 收敛为 6 节点纯审批流，23 种自动化节点愿景废弃** | 本报告取代该裁定 |
| 2026-09-27 | **本报告（用户决策）** | **工作流抽离为独立专业工作流引擎**：即使部分能力与编排引擎重叠，作为独立引擎也应完整具备 | 新基线 |

### 1.2 方向裁定的依据

1. **业务诉求**：平台的"流程自动化"需求（需求评审签字、发布审批、定时巡检、数据同步、通知推送等）与"多智能体协作"（LLM 推理链）是两类真实且不同的场景；编排引擎以 LLM 为中心、内存 Reactive 短周期执行，不适合承载"人机混合、等待数天、强审计治理"的流程语义。
2. **ADR-001 的现实检验**：编排引擎已落地（O1~O3），但工作流并未被替代——双轨是客观存在。"降级工作流为图执行器后端"会丢失工作流的差异化价值（持久化等待、人工任务治理、结构化审计）。
3. **用户裁定**：与编排重叠的能力（触发、变量、条件、并行、HTTP 集成等）作为独立工作流引擎**也应当完整具备**——重叠是两个专业引擎各自完整的自然结果，不是需要消除的浪费。

### 1.3 新定位（一句话）

> **工作流引擎 = 面向业务流程自动化的独立引擎**：触发驱动 + 节点编排 + 人在回路（HITL 审批治理为其差异化核心）+ 持久化等待执行模型 + 结构化审计；对标 n8n（节点自动化广度）与 Camunda/Flowable（BPM 治理深度）的能力交集，并与智能体编排引擎（LLM 协作专精）形成互补而非替代。

### 2.2 前端（演示态）

- `WorkflowCanvas.tsx`（658 行）纯 SVG 自绘：**保存是假按钮**（:475 仅 toast）、无撤销/缩放/框选/minimap、主题硬编码——46 号已评估"不建议深挖复用"；
- `workflowTypes.ts` **23 种节点愿景目录**（6 大类，完整清单见附录 A）：是纯前端静态声明（agentId/knowledgeBase 等为写死演示项），后端无一对应；
- 待办办理 UI 缺失：completeNode/listMyInstances/通知 API 前端零调用（B5 断点，48 号已确认）——流程发起后无人能推进；
- 状态字面量大小写错位（前端 'RUNNING' vs 后端 'running'）。

### 2.3 既有设计文档与实现的分化

| 文档 | 与实现的分化点 |
|---|---|
| 30 号 API 设计 V1.1 | activate/deactivate → 实现为 publish/archive；cancel → terminate；新增 graph 端点；**流转记录/独立 review/rollback/assign/通知 read-all/unread-count/全部监控 API/entityType 绑定/超时调度均未实现** |
| 31 号 UI 设计 V1.0 | antd + React Flow + Zustand + 8 路由——实际为 Tailwind + 自研 SVG + 单页 PageType；31 号未按文档落地，也不能作为现状快照 |
| PRD F-026~F-036 | 节点 8 类（含 gateway 并行网关/automation 自动化节点——DB 均无）；F-033 驳回回退原语、F-035 并行分支三种同步策略（ALL/FIRST/MAJORITY）均未实现；F-036 审计要求 AOP |

### 2.4 结论

工作流轨是**"骨架真实、能力极简、前后端断裂"**：执行内核（线性单节点推进）撑不起专业引擎所需的 DAG/并行/循环/异步自动化；23 节点愿景与 6 节点后端互为断层；既有的价值资产是**九张表的结构化持久化骨架**（节点/流转/实例/节点实例/通知/权限/审计——比编排的 JSON 原文更适合工作流的查询、审计与人工任务治理需求）与 30/31 号沉淀的语义决策。

## 三、业界专业工作流引擎能力模型

参照系：**n8n / Node-RED**（节点式自动化）、**Dify / Coze**（LLM 应用工作流）、**Camunda / Flowable**（BPMN 治理）、**Temporal**（持久化执行）。综合其公开能力面（来源见文末），提炼独立专业工作流引擎应具备的 **8 层能力模型**：

| # | 能力层 | 应有能力 | 业界对应 |
|---|---|---|---|
| C1 | **定义与版本** | 可视化定义、结构校验（悬空边/环/必填）、发布闸、不可变版本快照、执行绑定版本、导入导出、模板库 | n8n workflow 导出；Camunda process versioning |
| C2 | **触发体系** | 手动、定时（Cron）、Webhook（token/签名）、应用事件、上游流程/节点事件 | n8n trigger 节点族；Camunda message/timer start event |
| C3 | **执行内核** | DAG 图执行、**并行分支与汇聚**（ALL/FIRST/N-of-M 同步策略）、**循环**（逐项/直到条件）、条件与多路分支、子流程、**持久化等待**（人工任务/定时器挂起数天可恢复）、暂停/恢复/终止 | Camunda wait state + job executor；n8n execution model |
| C4 | **节点类型体系** | 六大类：逻辑控制、人工任务、数据处理、AI 能力、系统集成（HTTP/DB/邮件/IM）、流程控制；**节点注册表**（handler 可插拔、热扩展） | n8n 400+ nodes；Flowable 任务类型 |
| C5 | **数据与变量** | 流程变量（触发输入/节点输出/上下文）、表达式语言（比较/逻辑/路径取值）、节点间数据映射、结构化传递（防注入） | n8n JSON items + expressions；Camunda process variables |
| C6 | **人工任务治理**（差异化核心） | 办理/审批、**会签（ALL）/或签（ANY）/按比例**、超时升级与自动处理、委托与转办、驳回回退（到指定节点）、待办/已办/催办、通知（站内/邮件/IM） | Camunda human task + tasklist；Flowable case |
| C7 | **容错与可靠性** | 节点级重试（次数/退避）、超时、**错误分支**（onError 边）与 continue-on-error、死信记录、幂等触发 | n8n error workflow + retry；Camunda boundary error event + job retry |
| C8 | **可观测与治理** | 节点级执行记录与时间线、重放/调试、监控仪表盘（实例数/超时/失败率）、**审计日志**（操作/前后态/IP/耗时）、RBAC（发起/办理/审批/管理） | Camunda Cockpit/Optimize；PRD F-036 |

**关键执行模型差异（本次调研最重要的结构发现）**：

| | 编排引擎（现有） | 工作流引擎（目标） |
|---|---|---|
| 执行模型 | 内存 Reactive 流（一次执行全程在 Reactor 链上跑完，分钟级） | **持久化等待驱动**：人工任务/定时器可挂起数天，节点完成事件驱动推进，进程重启无损 |
| 状态存储 | JSON 原文快照 + 执行实例 | **结构化行**（node_instance 每节点一行，可查询/审计/分派） |
| 中心 | LLM 推理 | 流程正确性 + 人机协作治理 |
| 典型周期 | 秒~分钟 | 分钟~数周 |

这解释了为什么"统一到一个引擎"不可行：**把数天级人工等待塞进内存 Reactive 模型、或把 LLM 流式链塞进行级状态机，都会让两个引擎都退化为半吊子**。专业化的正确路径是各按其执行模型做深，重叠能力各自实现，互操作点显式定义（见 §六）。

## 四、差距分析：现状 vs 专业引擎标准

| 能力层 | 现状得分 | 差距（关键项） |
|---|---|---|
| C1 定义与版本 | 2/5 | 发布无校验、无版本快照机制、无导入导出 |
| C2 触发体系 | 1/5 | 仅手动；定时/Webhook/事件全缺（编排轨已有成熟模式可平移） |
| C3 执行内核 | 2/5 | 线性单节点；无并行/循环/子流程/异步自动化；人工任务持久化等待已有（唯一达标项） |
| C4 节点体系 | 1.5/5 | 后端 6 类无差异化 handler；23 类愿景零实现；无注册表框架 |
| C5 数据与变量 | 2/5 | variables JSON 有；表达式仅单比较；无结构化传递/映射 |
| C6 人工任务治理 | 2/5 | 办理/审批可用；无会签或签/超时升级/委托/驳回回退原语/待办 UI/通知推送 |
| C7 容错可靠性 | 0.5/5 | 无重试/超时/错误分支/死信（编排轨 WFO-05 模式可平移） |
| C8 可观测治理 | 2/5 | 审计落库（非 AOP）、通知无推送、无监控 API/UI、权限表零消费 |

**综合：约 1.7/5**——骨架真实但距"专业独立引擎"有系统性差距，需要一次以执行内核重构为核心的整体设计（51 号），而非逐点修补。

## 五、三套节点模型裁决

现状三套体系互不兼容：**PRD F-026（8 类审批语义）/ DB node_type（6 类）/ 前端愿景（23 类自动化语义）**。裁决如下：

1. **以"新统一节点体系"取代三套**（51 号 §三详细定义）：吸收前端 23 类的分类框架（触发器/逻辑/数据/AI/集成/流程控制）与全部自动化节点；**恢复并强化 PRD 中被前端愿景丢失的人工任务语义**（task/approval + 会签或签/超时升级——这是工作流引擎对编排引擎的差异化核心，Camunda 系的看家能力）；DB node_type 为 VARCHAR(32) 无需改列，扩为注册表键。
2. **并行语义裁决**：采用 PRD F-035 的 **parallel 网关 + join 汇聚**（三同步策略 ALL/FIRST/N-of-M）替代前端愿景中缺失的并行表达——与编排的 PARALLEL/MERGE 同构但实现于持久化模型。
3. **AI 节点裁决**：不重复造 LLM 执行器——`agent` 节点调平台智能体运行时、`orchestration` 节点调编排图（复用 `executeGraphForAgentTool` 入口模式）、`llm` 节点直连模型网关（简单补全场景）、`knowledge` 节点对接 Wenshi 检索——AI 深度能力归编排轨，工作流只做**调用与结果消费**。
4. **subprocess vs sub-workflow**：统一为 `sub-workflow`（引用另一工作流定义），DB 的 subprocess 语义并入。
5. **23 类逐条去向**：保留 21 类（all except：`counter` 降为 P2 可选、`rag` 更名 `knowledge` 并对接 Wenshi）；新增 `upstream`（上游流程触发）、`approval` 强化会签或签、`parallel`/`join` 网关——**目标节点集 26 类**。

## 六、与编排引擎的边界重定义（取代 28-V1.2 与 48 号裁定）

| 维度 | 编排引擎（LLM 协作专精） | 工作流引擎（流程自动化专精） | 重叠策略 |
|---|---|---|---|
| 执行模型 | 内存 Reactive（秒~分钟） | 持久化等待驱动（分钟~数周） | 各自核心，不共享 |
| 中心 | LLM 推理链 | 流程正确性 + 人机治理 | — |
| 触发 | 手动/API/定时/Webhook/Agent 工具 | 手动/定时/Webhook/事件/上游 | **各自完整实现**（模式可复制，代码不共享中间层） |
| 并行/条件/循环 | PARALLEL/MERGE/ROUTER（内存图） | parallel+join/condition/switch/loop（持久化 DAG） | **各自完整实现** |
| 版本化/校验 | VL 体系 + 版本快照 | WV 体系 + 版本快照 | **各自实现**（规则语义不同） |
| 人工介入 | HUMAN 关卡（审批中心） | task/approval 任务治理（会签/或签/升级/委托） | 工作流深度治理自持；**审批中心 UI 复用**（双 Tab 已有） |
| AI 能力 | 原生（AGENT 节点/四模式/自主目标） | **调编排/调 Agent 的桥接节点** | 显式互操作 |
| 互操作 | 编排图可被工作流 orchestration 节点调用 | 工作流定义可被 AI 引用（暂不实现反向触发，列后续） | 单向优先，最小化耦合 |
| 存储 | JSON 原文 + 版本表 | 结构化九表骨架（扩展） | 各按执行模型选型 |

> 该边界**取代 28-V1.2 的"审批流 vs Agent DAG"二分**与 **48 号"BPM 收敛纯审批流"裁定**；与 29-ADR-001 的关系：ADR-001 的"统一抽象"不再追求，"向后兼容导出"降级为远期可选项。

## 七、需求映射与结论

| 需求源 | 条目 | 新方案覆盖 |
|---|---|---|
| PRD | F-026（8 类节点）| 节点体系 26 类（§五裁决），gateway→parallel+join，automation→注册表自动化节点 |
| PRD | F-032 节点输出传递 | 变量系统升级（BR-022 结构化传递） |
| PRD | F-033 驳回回退 | approval 驳回 → 回退到指定前驱节点（原语级，原 48 号用条件边简化的方案升级） |
| PRD | F-034 暂停恢复 | 持久化等待模型天然支持（节点级） |
| PRD | F-035 并行分支（P2） | parallel+join 三同步策略 |
| PRD | F-036 审计 AOP+180 天 | 审计切面 + 保留策略 |
| PRD | BR-018/022/023/024 | 发布闸/结构化传递/驳回回退原语/暂停恢复 |
| 前端愿景 | 23 类节点 | 26 类统一体系（21 保留+2 强化+3 新增，counter 降级） |
| 30 号 | 未实现 API（监控/流转记录/回退/通知 read-all） | 纳入 51 号 API 设计 |
| 用户裁定 | 重叠能力完整具备 | C1~C8 全层设计，重叠各自实现（§六） |

**结论**：立项"独立专业工作流引擎"整体重构，设计实现方案见 `docs/design/51-workflow-engine-design-implementation.md`（目标架构 / 26 类节点体系 / 数据模型 / 持久化等待执行内核 / 触发体系 / 人工任务治理 / 互操作 / API / 分期实施计划，总估算 31~41 人日）。
