## 二、P4-B 多副本化立项卡片（建议本轮立项，P0）

> 溯源：AE-P0-5（veloflow 单实例约束）+ 报告 P2-8（interface 挂起/Tomcat 同窗）+ 45 号 §四遗留——AE-PLAN §6 原卡片承接。

### 2.1 目标与质量属性（铁律②量化）

| 属性 | 现状（单副本假设） | 目标（2 副本 interface） | 验收方式 |
|---|---|---|---|
| 会话流连续性 | 单实例内存直发 | 副本故障/轮询切换时 SSE 不断流（Redis Pub/Sub 广播） | 双副本压测：kill 一副本，进行中流 ≤3s 恢复 |
| 编排暂停/恢复 | ExecutionControl 内存注册表 | 跨副本可恢复（检查点已在 DB——DbOrchestrationCheckpointStore 已就绪✓） | 副本 A 暂停 → 副本 B resume 成功 |
| veloflow 实例并发 | ReentrantLock 单实例 | 多副本下实例状态机不撕裂 | 并发 completeNode 压测零撕裂 |
| 挂起延迟 | HTTP 同步 | P99 < 5ms（Redisson 本地）或 ≤15ms（DB CAS） | 基准测试 |

### 2.2 技术选型（铁律①：≥2 方案对比留 ADR）

| 决策点 | 方案 A | 方案 B | 建议 |
|---|---|---|---|
| 分布式锁 | **Redisson**（RLock，TTL 看门狗；依赖=已有 Redis——SSE distributed 已预留 Redis Pub/Sub） | **DB CAS**（UPDATE ... WHERE status=expected，零新依赖，复用 MyBatis-Plus；吞吐受限但编排并发低） | **建议 DB CAS 优先**：编排/veloflow 实例级并发为低频操作（人工触发+定时），DB CAS 零新组件即可满足；Redisson 仅当 CAS 实测吞吐不足时升级（ADR-4B-1 留档） |
| SSE 跨实例广播 | Redis Pub/Sub（gewu.sse.distributed=true，**代码已预留**） | 会话粘性（网关按 sessionId 哈希） | **两者叠加**：粘性为第一道（网关已具备路由能力），广播兜底副本故障；仅开粘性则故障切换丢流 |
| 引擎内存态执行上下文 | 粘性路由（网关 sessionId 哈希到固定副本） | 上下文外置化（Redis/DB 序列化 BudgetContext+消息列表） | **粘性优先**：外置化需序列化整个会话执行态，工程量大且有兼容风险；粘性+副本故障时该会话失败重试（可接受，登记） |

### 2.3 范围与边界

**做**：①网关 sessionId 粘性路由配置与验证 ②SSE distributed **部署态生效验证**（F-02 据实校正：helm values.yaml L73 已置 `sseDistributed: "true"` + L70 `redisHost: dragonfly`——配置侧已就绪，本项为验证而非开启；Redis 故障=流断为**现状**而非变更后风险）③ExecutionControl/veloflow 锁 DB CAS 化（接口不变）④interface 挂起/Tomcat 3.2→3.3 升级同窗评估（45 号遗留，多副本变更前必须核）⑤双副本端到端压测与故障演练。
**不做**：编排执行态外置化（粘性+失败重试覆盖）；veloflow 多活仲裁（单活语义保持，锁保证）。

### 2.4 工作量与风险

工作量 ≈ **8 人日**（粘性路由 1 + SSE 广播 1 + DB CAS×2 处 2 + Tomcat 评估 1 + 压测演练 2 + 缓冲 1）。
**风险**：①Redis（现网 dragonfly）已是会话流跨实例依赖（F-02 校正：sDistributed 已配置）——Redis 故障=流断为现状风险，粘性优先 + Redis 高可用为缓解；②DB CAS 在高并发下重试膨胀 → 编排低频场景可控，压测验证；③Tomcat 升级若引入回归 → 同窗灰度（先升级后切多副本）。

### 2.5 前置条件（需用户/运维确认）

1. helm chart replicas=2 是否已实际部署（或仅 chart 就绪）——**决定敞口紧迫度**；
2. Redis 是否在部署清单（SSE distributed 前置）；
3. Tomcat 3.3 升级窗口是否可与本项合并。

## 三、P4-D 评测 CI 门禁立项卡片（建议本轮立项，P1）

### 3.1 目标

把 45 号预承诺评测从"人工触发"变为"引擎 CI 门禁"：核心包改动时自动跑 20 题题集，质量基准棘轮（评分均值不降 +5% 容差内）+ 成本/时长不超阈值，未过则阻断合并。

### 3.2 选型对比（铁律①）

| 方案 | 内容 | 取舍 |
|---|---|---|
| A：CI 阶段全量跑批 | 每次 PR 跑 20 题×3 组 | 信号最强，但 LLM 成本/时长高（120 次调用/PR） |
| B：定时跑批 + 结果棘轮 | 每夜/每周跑批，结果写基准文件，PR 只比对棘轮 | **建议**：LLM 成本可控（每周 120 次），PR 门禁只做本地对比（零 LLM） |

### 3.3 范围与工作量

跑批调度复用 AE-P1-3 触发器基建；基准文件（quality-baseline.json）入库；PR 门禁脚本比对棘轮（±5% 容差内放行，超出标红待评）。工作量 ≈ **3 人日**。风险：Judge 供应商波动 → 双 Judge 取中位数（45 号已有多 Judge 经验）。
