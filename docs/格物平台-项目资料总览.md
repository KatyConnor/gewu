## 1. 项目概述

### 1.1 项目定位

**格物平台**是一个 AI 驱动的智能开发协作平台，提供 Agent 智能体会话、工作流编排、代码沙箱执行、项目管理等核心能力，并通过 Wenshi 架构为 LLM 提供知识增强。

### 1.2 核心能力

| 能力域 | 功能 | 状态 |
|--------|------|------|
| 用户认证 | JWT 认证、RBAC 权限、国密加密 | ✅ |
| 项目管理 | 项目 CRUD、成员管理、权限分配 | ✅ |
| 会话管理 | 消息历史、SSE 实时推送、已读状态 | ✅ |
| Agent 系统 | Agent 配置、工具绑定、执行引擎 | ✅ |
| 工作流引擎 | 流程编排、状态机、并行流程 | ✅ |
| AI 对话 | 流式对话、多模型支持、上下文管理 | ✅ |
| 沙箱执行 | 代码隔离、资源限制、安全策略 | ✅ |
| Wenshi 增强 | 知识层、推理层、学习层三层增强 | ✅ |
| 监控告警 | 全链路监控、实时告警、可视化 | ✅ |

## 2. 技术架构

### 2.1 架构风格

**模块化单体 + 微服务混合**：当前阶段采用 Maven 多模块单体部署，未来演进为微服务架构。

```
当前阶段（开发期）：
  Maven 多模块单体部署
  ├── gewu-interface    ← API 网关 + Controller
  ├── gewu-application  ← 业务逻辑
  ├── gewu-domain       ← 领域实体
  ├── gewu-infrastructure ← 基础设施
  ├── gewu-gateway      ← 独立网关服务
  ├── gewu-sandbox      ← 独立沙箱服务
  └── gewu-common       ← 公共工具

未来演进（生产期）：
  微服务拆分
  ├── gewu-auth-service     ← 认证服务
  ├── gewu-agent-service    ← Agent 服务
  ├── gewu-workflow-service ← 工作流服务
  ├── gewu-sandbox-service  ← 沙箱服务
  └── gewu-wenshi-service   ← 知识增强服务
```

### 2.2 分层架构

| 层级 | 职责 | 对应模块 |
|------|------|----------|
| **表现层** | Web 前端、桌面客户端、移动端 | gewu-web |
| **接口层** | REST API、WebSocket、SSE | gewu-interface |
| **应用层** | 命令处理、查询处理、DTO 转换 | gewu-application |
| **领域层** | 会话聚合、Agent 聚合、Tool 聚合 | gewu-domain |
| **基础设施层** | 持久化、缓存、事件发布、LLM 客户端 | gewu-infrastructure |

### 2.3 核心设计原则

| 原则 | 说明 |
|------|------|
| **分层架构** | 表现层、应用层、领域层、基础设施层清晰分离 |
| **DDD** | 领域驱动设计，业务逻辑封装在领域层 |
| **多数据库支持** | OceanBase/MySQL/PostgreSQL/Oracle |
| **信创合规** | 100% 满足信创目录要求 |
| **自主可控** | 自研 API 网关、自研工作流引擎 |

## 7. Wenshi 知识增强架构

### 7.1 架构定位

> **给企业已部署的大模型装上"记忆+知识+经验"三层增强，让 LLM 越用越聪明。**

### 7.2 三层架构

| 层级 | 职责 | 核心组件 |
|------|------|----------|
| **知识层** | 结构化记忆 | 语义记忆、情景记忆、程序性记忆、参数化记忆 |
| **推理层** | 思维编排 | Planner、SolverRouter、Critic |
| **学习层** | 经验进化 | 经验抽取、质量评估、技能演化、反思复盘 |

### 7.3 适配层

| 组件 | 职责 |
|------|------|
| **LlmAdapter** | 模型适配（DeepSeek/Qwen/OpenAI） |
| **EmbedAdapter** | 嵌入适配（BGE-small/LLM 原生） |
| **VectorStoreAdapter** | 向量库适配（pgvector/Milvus） |
| **TenantIso** | 租户隔离 |

### 7.4 数据流

```
用户输入 → Language Interface → Planner → SolverRouter → Critic → 输出
                ↑                    ↑          ↑
                │                    │          │
           记忆注入               经验库      知识库
```

| CR-017 | 密码哈希不安全 | SM3 → Sm3PasswordEncoder 适配器 |

## 附录 A：关键决策记录 (ADR)

### ADR-001: 选择分层架构 + DDD

**状态**: 已批准  
**决策**: 采用分层架构 + DDD 模式，业务逻辑封装在领域层。  
**理由**: 清晰的分层结构，职责明确；DDD 提升业务建模能力；易于测试和维护。

### ADR-002: 选择 OceanBase 作为主数据库

**状态**: 已批准  
**决策**: 选择 OceanBase 作为主数据库。  
**理由**: 分布式数据库，支持海量数据；MySQL/PostgreSQL/Oracle 兼容；信创合规。

### ADR-003: 自研 API 网关

**状态**: 已批准  
**决策**: 自研 API 网关 (Java/Netty)。  
**理由**: 信创合规要求；自主可控；性能可定制。

### ADR-004: 选择 Firecracker 作为沙箱运行时

**状态**: 已批准  
**决策**: 选择 Firecracker 作为沙箱运行时。  
**理由**: 硬件级隔离，安全性高；轻量级，开销小。

### ADR-005: 自研工作流引擎

**状态**: 已批准  
**决策**: 自研工作流引擎。  
**理由**: 业务定制化需求；避免第三方依赖；性能可控。

### ADR-006: 选择 DragonflyDB 作为缓存

**状态**: 已批准  
**决策**: 选择 DragonflyDB 作为缓存。  
**理由**: 100% Redis 协议兼容；性能优于 Redis；内存效率高；信创合规。

### ADR-007: 选择 Nightingale 作为监控平台

**状态**: 已批准  
**决策**: 选择 Nightingale 作为监控平台。  
**理由**: Open-Falcon 继承者；活跃维护；信创合规；功能完善。
