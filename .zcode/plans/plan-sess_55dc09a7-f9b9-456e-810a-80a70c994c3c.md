# 「任务未执行完即总结收场」根因分析与修复方案（待审核）

## 一、根因分析（日志证据链已闭合）

**结论：这次不是任何熔断器触发，而是"会话历史加载压缩"在任务开始时摧毁了任务连续性，导致模型自行总结收场。**

### 证据链（今日 18:10 的执行，即你截图的会话）

1. **无任何熔断触发**：12 轮、累计 47.7K tokens，全程无"预算熔断"WARN、无轮次闸门（50 轮上限）、无死循环检测、无执行内上下文压缩日志；结束于 `recordSuccess`（正常完成，模型自己选择输出总结）——上次修复的三个熔断点今天全部没有触发（未绑定用户 token 不限量 ✓ 轮次 50 ✓）
2. **关键事件在执行开始前一瞬**（18:10:42）：`SessionContextService: 会话上下文超过 token 阈值，触发压缩: estimatedTokens=10799`
3. **代码定位**（`SessionContextService.java`）：
   - `TOKEN_THRESHOLD = 4000`（**硬编码**）：会话历史估算超过 4000 tokens（≈1.6 万字符）就压缩——一条带文件卡片/过程元数据的 assistant 消息就可达 2-4K tokens，长程任务几轮就超
   - `COMPRESSED_KEEP_RECENT = 6`（**硬编码**）：只保留最近 6 条消息（≈3 轮对话），**其余全部压成 ≤4000 字摘要**（`[对话历史摘要]` 一条 system 消息）
4. **效果链**：模型收到的是"旧对话的一段粗摘要 + 最近 3 轮"——早期轮次的任务计划（`<!--PLAN:-->` 标记）、文件产出、工具结论全部丢失 → 模型判断"任务基本完成" → 输出交付总结 → 你看到"没执行完就总结报告"，因此前真熔断过而误判为又被熔断

### 为什么之前没暴露

此前任务先被旧 82K token 预算熔断（轮次根本走不到积累长历史）；熔断修复后任务跑得久、历史快速膨胀，**加载压缩这个低阈值硬编码的"隐形杀手"浮出水面**——它是链式根因的下一环。

另核实：执行内自动压缩续跑未生效的原因是 `model_config.context_window_input` 尚未配置（该功能依赖管理员在模型配置里填窗口值），见修复第 4 项。

## 二、修复方案（1 个主改动 + 3 个配套）

### 1. 压缩阈值与保留策略配置化并大幅提高（核心）
`SessionContextService`：
- `TOKEN_THRESHOLD = 4000` → `@Value("${gewu.session.context-compact-threshold-tokens:32000}")`（**4000 → 32000**）
- `COMPRESSED_KEEP_RECENT = 6` → `@Value("${gewu.session.context-compact-keep-recent:24}")`（**6 → 24**，≈最近 12 轮对话）
- 两处使用点（`buildContextMessages` L69、`compressContext` L150）同步改用配置值
- `application.yml` 显式配置这两项（注释说明：对齐模型上下文窗口的 1/4 左右，长程任务建议 32K 起）

**论证**：32K 阈值 ≈ 13 万字符历史，配合模型 128K 窗口仍有充足生成空间；24 条保留覆盖最近 1-2 次完整 agentic 执行（含其全部文件卡片与 PLAN 标记），任务连续性完整。

### 2. 任务计划快照跨压缩存活（任务连续性保险）
压缩旧消息前，扫描被压缩区间提取**最后一个** `<!--PLAN:{...}-->` 标记段，压缩结果后追加一条 system 消息 `[任务计划快照]\n{plan}`——即使触发压缩，模型仍能看到完整任务清单与步骤状态。

### 3. 压缩摘要与保留区的提示词强化（小改）
`[对话历史摘要]` 前缀文案追加一句："以下是早期对话的摘要，任务可能尚未完成，请结合任务计划快照与最近消息继续执行，勿仅凭摘要判断任务已完成"——对冲模型"读到摘要即收尾"的倾向。

### 4. 模型上下文窗口配置（数据操作，非代码）
在**管理端 → 模型配置**为所用模型（如 glm-5.3-flash）填写 `context_window_input`（如 128000）与 `context_window_output`（如 16384）——这是"执行内自动压缩续跑"生效的前提（超窗口时压缩历史继续跑，而非中断）。此项需你操作或告诉我各模型的准确窗口值，我写入种子迁移。

## 三、影响面

| 项 | 评估 |
|---|---|
| SessionContextService | 阈值/保留配置化 + PLAN 快照提取 + 文案，改动集中一个文件 |
| 行为变化 | 历史压缩从"4K 即压、只留 6 条"放宽到"32K 才压、留 24 条 + 计划快照"——长任务上下文完整度大幅提升；旧会话无影响（压缩是加载时内存行为，不回写 DB） |
| token 成本 | 每轮请求携带的历史变长（最多 32K），长会话单轮成本上升——这正是任务连续性的必要代价，且由模型窗口兜底 |
| 测试 | SessionContextServiceCompressionTest 适配配置注入；全模块回归 |

## 四、手工回归清单
1. 重启后端后重跑同类长任务（跨多轮"继续"）：模型能引用早期轮次的计划与文件状态，不再提前总结收场
2. 日志确认：`触发压缩` 出现频率显著下降，且出现时保留 24 条 + 计划快照
3. 超长会话（>32K tokens）压缩后：模型仍能准确说出任务清单进度
4. 配置窗口值后：超长上下文任务看到"上下文接近模型窗口，已压缩历史"状态行后继续执行
5. 原有熔断回归（轮次/banner/总结标记）不受影响
