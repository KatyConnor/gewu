# LPU 规则 · 02 骨架阶段（S1 · SKL）

> 目标：从目录结构还原模块清单与依赖关系，形成后续五维深潜的"骨架地图"。
> 骨架 = 模块清单 + 依赖图 + 分层判断。仍然只读、粗粒度。

---

### LPU-SKL-001【M】模块清单成文
输出模块清单到 findings（C 维初始段），每模块登记：
`模块名 / 物理路径 / 一句话职责猜测 / 依据（目录名+代表文件）/ 置信度`。
职责猜测在此阶段允许 B/C 级，S2 深潜时逐一验证或推翻。

### LPU-SKL-002【M】依赖方向图
识别模块间依赖（import/require/use 关系聚合到模块级），以文本邻接表记录：

```
order-service → inventory-api, payment-api, common-util
web           → order-service, user-service
```

- 检测**循环依赖**：发现即登记到 debt-risks 候选（编号留空，S5 正式定级）；
- 依赖图是架构图（architecture.md）的骨架，文本邻接表即草稿。

### LPU-SKL-003【M】分层模式判定
判断项目采用的模式并给证据：MVC / 前后端分离 / 单体分层 / 微服务 / 模板渲染单体 /
事件驱动。判定依据：目录命名规律 + 入口类型分布（RCN-003 的产出）。
前后端同仓时（如 JSP+Servlet 或 Vue 混在 src/main/webapp），显式记录"混合形态"。

### LPU-SKL-004【R】公共组件识别
识别横切组件（工具类库、公共异常、认证过滤器、日志切面）并单独登记。
公共组件是理解成本的放大器：被依赖越多，优先级越高（S2 排序依据）。

### LPU-SKL-005【M】模块分析排序
按以下优先级确定 S2 深潜顺序（写入 PROGRESS）：
1. 业务核心模块（入口数多 + 依赖它的模块多）；
2. 公共组件（被广泛依赖）；
3. 疑似死代码（最后分析，或按 O 级跳过但需登记）。

### LPU-SKL-006【R】死代码初筛
无入口引用、无依赖指向、git 历史长期不活跃的模块标记为"疑似死代码 [C]"，
交由 S3 交叉验证复核。禁止在骨架阶段直接判定删除——遗留项目"看似死实际被脚本/反射调用"是常见事故源。

### LPU-SKL-007【M】骨架地图落盘
骨架阶段完成标志：模块清单 + 依赖邻接表 + 分层判定写入 findings，PROGRESS 更新至 S2，
并锁定第一个深潜模块。**每个模块深潜前重申该模块在依赖图中的位置（上游/下游），带着依赖上下文去读代码。**
