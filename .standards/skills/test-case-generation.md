# 技能模块：test_case_generation

> 测试用例设计，覆盖正常 / 边界 / 异常 + AI 专项测试。

## 1. 技能描述

本技能基于需求文档与功能描述，采用等价类划分、边界值分析、场景法、决策表、状态迁移等方法设计测试用例集，覆盖正常 / 边界 / 异常三类场景。针对 AI 应用额外补充 AI 专项测试（意图识别准确率、内容合规、幻觉识别、抗提示词注入）。输出测试用例集 + 自动化脚本 + 预期结果。

## 2. 触发条件

- 输入包含「测试用例」「用例设计」「测试覆盖」「自动化测试」等关键词
- 已提供需求文档 / 功能描述 / 接口契约
- 业务类型明确（C 端 / B 端 / AI 应用）
- 测试框架与执行环境已确定

## 3. 执行步骤

1. **需求分析**：解析需求文档，提取功能点、业务规则、约束条件、用户旅程。
2. **测试策略选择**：
   - 等价类划分：有效 / 无效等价类
   - 边界值分析：上界、下界、临界值
   - 场景法：基本流、备选流、异常流
   - 决策表：多条件组合
   - 状态迁移：状态机覆盖
3. **设计正常用例**：覆盖业务主流程、正向链路、典型场景。
4. **设计边界用例**：参数边界、空值、极值、并发、超时。
5. **设计异常用例**：异常输入、依赖故障、权限不足、资源耗尽。
6. **AI 专项测试**（如适用）：
   - 意图识别准确率（同义改写、多轮上下文）
   - 内容合规（敏感词、价值观、政治正确）
   - 幻觉识别（事实核查、引用追溯）
   - 抗提示词注入（越狱、Prompt Injection）
   - 多模态一致性（图文匹配）
7. **生成自动化脚本**：基于框架（Pytest / TestNG / Cypress）输出可执行脚本。
8. **输出测试矩阵**：用例编号、模块、类型、优先级、预期结果。

## 4. 输入规范

```yaml
任务类型: 测试用例设计
需求文档: [PRD 链接]
功能描述: 用户注册 + 实名认证
接口契约: [OpenAPI 文档]
业务类型: C端 + AI（智能客服）
测试框架: Pytest + Allure
覆盖率门禁: 核心95% / 普通85%
AI专项: 启用
```

## 6. 质量标准

- 用例必须覆盖正常 / 边界 / 异常三类场景，缺一不可
- 核心模块用例覆盖率 100%，普通模块 ≥ 85%
- AI 应用必须包含意图识别、内容合规、幻觉识别、抗注入四类专项
- 每个用例必须有明确的预期结果与可验证断言
- 自动化脚本必须独立可重复运行
- 用例命名规范：`模块_场景_期望`

## 7. 风险控制

| 规则 | 内容 |
|------|------|
| RISK-01 | 禁止使用违规 / 敏感内容作为 AI 测试输入 |
| RISK-02 | 用例设计必须基于需求，禁止凭空臆造场景 |
| RISK-03 | 自动化脚本必须包含数据清理逻辑，避免脏数据 |
| RISK-04 | AI 专项测试必须有人工复核环节，避免误判 |
| RISK-05 | 测试数据不得包含真实用户数据，必须脱敏 |
| RISK-06 | 高优先级用例必须在提测后 24 小时内执行 |

## 9.3 测试金字塔分层纪律（V2.0 增补）

- 分层配比：单测（04，行 100%/分支 ≥85%）为塔基 → 接口层（04 契约测试+06 接口自动化）为塔身 → 端到端（06）为塔尖；上层失败优先怀疑下层缺失。
- 与 04 V2.0 边界：契约测试（接口兼容性）归 04；业务正确性与端到端归 06。

## 9.4 视觉回归测试（V2.1 增补 · 渲染级验证——与 11 号容差判据分权）

> 触发条件：界面/样式系统/响应式断点/组件库/字体变更。基线判定与容差标准归角色 11（ui-design CHK-30/31），执行与门禁归 06。

- **基线管理**：截图基线版本化入版本库，与代码同版本提交；基线变更必须附 11 号容差判定记录（防基线漂移静默通过）。
- **对比策略三档**：①布局断言优先（元素位置/尺寸/可见性——比像素稳，抗抗锯齿噪声）②像素 diff（容差阈值+忽略区域清单）③组件级快照路径（组件隔离，变更定位到组件）。
- **防抖三件套**：禁用动画与过渡 / 等待字体加载与网络空闲 / 固定视口尺寸与 DPR——任一缺失 = 假红温床。
- **判定分级**：像素级一致（关键页）/ 布局级一致（常规页）/ 语义级一致（内容页）——按 11 号登记的页面级别适用。
- **盲区申明**：DOM 变化未渲染不可测；纯交互感受（hover 手感/动效体验）不在截图域，由 11 号走查承接——视觉回归**不冒充全验证**。
- **R-09**：基线未版本化 = 视觉门禁失效；**R-10**：像素 diff 无容差 = 噪声洪水；**R-11**：防抖缺失即出报告 = 假红违规。

## 9.5 体验量化指标（Core Web Vitals · V2.1 增补）

> 用户端体验的可量化层——与 §9.2 性能压测分界：9.2 管服务端容量（QPS/吞吐），9.5 管浏览器实测体验。

| 指标 | 阈值基线 | 度量什么 |
|------|---------|---------|
| LCP | ≤ 2.5s | 加载体验（最大内容绘制） |
| INP | ≤ 200ms | 交互响应延迟 |
| CLS | ≤ 0.1 | **视觉稳定性**（累积布局偏移——视觉体验的直接量化） |

- 三指标入性能测试报告必填项（真实浏览器实测，非服务端推算）；劣化即准出门禁项；阈值按产品线登记可收紧不可放空。

## 9.6 模糊需求用例派生（V2.2 增补 · 外源接测路径）

> 外源接测场景（UTSS V1.2 三·B）需求常常不完整——用例派生不凭直觉，按**需求模糊度三档**走不同路径，
> 铁律 3（用例可追溯）不破：派生用例必标 source。

| 模糊度档 | 判据 | 派生路径 | 用例标注 |
|---|---|---|---|
| **清晰** | 需求有明确验收条件/可测语句 | 直接映射 GWT（Given/When/Then 全三段可写） | source=requirement |
| **模糊** | 有意图无细节（"登录要好用""页面改版"级别） | 需求期望映射骨架 + **分支代码分析补全**（diff 改动面→功能点→补 When/Then 细节与边界值） | source=code-analysis |
| **空白** | 无需求材料或不可判读 | **探索式测试**（会话 charter：时间盒+风险驱动+漫游路线）+ 改动面风险排序定深度 | source=exploratory |

- 模糊/空白档用例执行后若行为与"合理用户预期"冲突：缺陷单如实登记（预期依据写入缺陷单 expected 字段），**禁止**因"需求没写"而豁免。
- 派生用例占比入测试报告（高占比=需求质量回执，反馈上游）；模糊度评级写入 registration.md（S1 受理登记）。
