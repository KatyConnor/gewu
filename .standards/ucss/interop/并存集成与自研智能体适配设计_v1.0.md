| 项 | 值 |
|---|---|

## 0. 文档定位

解决两个问题：

- **场景 A（并存集成）**：目标智能体或项目**已经集成了其他标准规范/能力**（企业内部安全编码规范、既有 Semgrep/CodeQL 门禁、既有测试流程规范、自有扫描技能等），要求 UCSS+UTSS 集成进去时**不干扰、不破坏、不覆盖**既有标准。
- **场景 B（自研适配）**：**自研智能体**（非 ZCode / Claude 生态的自有 runtime）要在同样的场景（代码扫描、测试验证）下按统一契约接入本姊妹规范。

**第一设计决策：本卷不改 UCSS v1.1 / UTSS v1.1 的任何冻结内容。** 全部并存与适配能力以附加层（本卷文档 + interop 配件 + tools 工具）实现。这本身就是「非侵入演进」的第一次实践——我们升级自己的生态时也不触碰已冻结基线，与对目标环境的要求同一纪律。

## 1. 术语

| 术语 | 定义 |
|---|---|
| 宿主标准 | 目标环境中已存在并运行的其他标准规范/能力（安全规范、测试流程、扫描工具门禁等） |
| 侵入面 | 新标准集成时可能与宿主标准发生干涉的具体接触点（§2 列 7 个） |
| 域内权威 | 某一治理域（如 SAST 门禁、测试准出）内拥有裁决权的标准 |
| M0~M3 | 渐进集成模式阶梯（§7）：观察 → 顾问 → 并行门禁 → 域内主导 |
| 互证（corroboration） | UCSS 与宿主标准对同一问题各自独立报出，属增强证据而非重复计数 |

## 2. 冲突面分析（七个侵入面）

逐面给出「侵入表现 + 本设计的消解手段」。后文各节展开。

| # | 侵入面 | 具体表现 | 消解手段 |
|---|---|---|---|
| F1 | 技能命名空间 | `code-scan` 是高度通用目录名，宿主 skills 目录可能已有同名技能——直接 `cp -r` 即**静默覆盖** | §4.1 装前冲突检测（coexist_check.py），冲突时不安装、给三个消解选项 |
| F2 | 环境与文件系统 | `UCSS_NETWORK_MODE` 环境变量、`~/.ucss/cache/` 缓存写入 HOME | §4.2 变量已前缀化天然隔离；缓存仅 SYNC 模式触达且限自有目录 |
| F3 | CI 门禁权威 | 宿主已有门禁（如 `semgrep --error`），新增门禁改变 stage exit code → **破坏既有流水线** | §7 M0 起步（`--summary-only`，exit 0）+ §8 stage 物理隔离，M2 仅对去重后的**独有发现**负责 |
| F4 | 报告口径 | 严重度词表不一致（error / 高危 / Critical）→ 看板双计或漏计 | §5.1 机器可读等级映射 + §5.2 去重键（cwe+file+line±3） |
| F5 | 流程触发 | 宿主智能体已有「测试」「扫描」类技能，触发词重叠 → 双技能同时激活抢流程 | §4.4 共存环境显式调用协议（「按 UCSS 扫描」「按 UTSS 测试」） |
| F6 | 产物落位 | UTSS `init_test_docs.py` 写 `tests/qa/` 五件套——共享路径，宿主测试文档可能已占用 | §4.3 落位协商：子命名空间 `tests/qa/.standards/utss/` 或字段级合并（§5.3） |
| F7 | 上下文预算 | 双技能 SKILL.md 同时驻留上下文，token 竞争 | §4.4 量化：单技能 SKILL.md ≈2~3K token，references 按需加载（渐进披露为 v1.1 既有设计） |

## 3. 并存三原则

1. **不覆盖（No Overwrite）**：任何安装/写入动作前先探测；冲突即报告、不覆盖、等人裁决。
2. **不接管（No Takeover）**：宿主标准的管辖域内，UCSS/UTSS 默认只观察不裁决；门禁权力只能经 §7 的阶梯逐级获得。
3. **可退场（Reversible）**：卸载零残留——无全局注册表、无守护进程、无外部副作用；退出路径见 §10。

## 4. 隔离机制设计

### 4.1 命名空间隔离（对应 F1）

技能包真实身份由 SKILL.md frontmatter 承载：UCSS `name: code-scan`（metadata.standard: UCSS-1.0），UTSS `name: utss-test-standards`。

**装前必检**（`tools/coexist_check.py`，本卷随附）：

```
python3 集成适配设计_v1.0/tools/coexist_check.py --skills-dir ~/.zcode/skills
```

检测两类冲突：① 目录名冲突（`code-scan` / `utss` 已存在）；② name 字段冲突（目录名不同但 SKILL.md `name:` 相同——同样抢触发）。

检出冲突时**拒绝安装**并给出三个消解选项：

| 选项 | 操作 | 适用 |
|---|---|---|
| O1 改名安装 | 目录改 `code-scan-ucss`，同步改 SKILL.md `name:` 字段 | 宿主同名技能要保留 |
| O2 分层安装 | 宿主技能留全局，UCSS 装项目级 `<项目>/.zcode/skills/` | 只在特定项目引入 |
| O3 人工合并评审 | 两技能 diff 对照，能力并轨后出单一技能 | 两套本就同源/重复建设 |

> 注意 O1 的代价：改名会改变触发行为的可预期性（description 中触发词不变，但 name 引用失效）。共存环境下推荐配合 §4.4 显式调用协议使用。

### 4.2 配置隔离（对应 F2）

- 环境变量：仅 `UCSS_NETWORK_MODE` 一个，已带 `UCSS_` 前缀，无撞名风险；
- 缓存：`~/.ucss/cache/`，仅 SYNC 模式（`sync_resources.py`）触达，目录自有、整删即净；
- 本卷新增的 `coexistence_modes.yaml` 是**集成方自己的文件**，放集成方仓库（如 `.ucss/`），**不写技能包目录**——技能包保持只读制品。

### 4.3 产物落位协商（对应 F6）

UTSS 五件套（计划/用例/执行/缺陷/报告）默认落 `tests/qa/`。落位协商规则（按序判定）：

1. `tests/qa/` 不存在或为空 → 按默认落位（同时创建）；
2. 目录存在但无同名五件套 → 并列落位，文件名不变（`test-plan.md` 等通用名若已被占用 → 进入 3）；
3. 同名文件已存在 → 子命名空间 `tests/qa/.standards/utss/`（隔离落位）；
4. 宿主要求单文档合并 → 字段级映射（§5.3），UTSS 12 字段逐项并入宿主模板，缺字段以宿主为准、UTSS 独有字段（业务规则出处/前置数据/设计方法标注）以附注列补齐。

> 现状限制：`init_test_docs.py` v1.1 尚无 `--dry-run` 与 `--output-subdir` 参数（backlog，见 §12），规则 3/4 当前由人工执行，脚本侧不自动越权。

### 4.4 上下文与触发隔离（对应 F5/F7）

- **显式调用协议**：共存环境（同域已有其他技能）中，团队约定用带名调用——「按 UCSS 扫描」「按 UTSS 跑测试」；不带名时由宿主智能体按其既有路由决定。单技能环境无此要求，触发词表见各自 SKILL.md description。
- **上下文预算**：UCSS SKILL.md 8.5KB、UTSS 9.1KB（约 2~3K token/个），加载后常驻；references 共 15 个文件**全部按需加载**（两 SKILL.md 均已内建「文件路由表」）。共存最坏情形（双标准 + 宿主双技能）常驻增量 ≈5~6K token，可接受；如仍紧张，可用 O2 分层安装把非项目域技能隔离在项目外。

## 5. 互操作层设计

### 5.1 等级映射（对应 F4）

机器可读映射随卷交付：`interop/severity_map.json`。要点：

**映射只用于展示、汇总与去重；门禁判定永远使用原始等级。** 防止「error 聚合了 Critical/High」这类有损映射反过来稀释阻断语义。

UCSS 五级 → 常见宿主词表：

| UCSS | SARIF level | Semgrep | CodeQL | 奇安信代码卫士 | OWASP Risk |
|---|---|---|---|---|---|
| Critical | error | ERROR | error | 严重 | Critical |
| High | error | ERROR | error | 高危 | High |
| Medium | warning | WARNING | warning | 中危 | Medium |
| Low | note | INFO | recommendation | 低危 | Low |
| Info | none | INFO | recommendation | 提示 | Info（注记级） |

已知有损点（在 json 中同样声明）：

- SARIF 仅 3 档有效（error/warning/note），Critical 与 High 聚合为 error，Low 与 Info 聚合为 note。反向消费时，`ucss_gate.py` 的现行标注为 error→"Critical/High"、warning→"Medium"、note→"Low/Info"——聚合语义如实标注，不虚拆；
- UTSS 侧无严重度词表冲突点（结论三值 PASS / PASS-WITH-RISK / FAIL 自成体系，不与宿主缺陷等级混用）；缺陷定级对接宿主系统时按 `references/07-defect-mgmt.md` 的级别表映射。

### 5.2 SARIF 中性交换与去重（对应 F3/F4）

SARIF 2.1.0 是与宿主工具链的**唯一交换格式**：`ucss_gate.py` v1.1 已可消费任意工具的 SARIF（读 tool driver.name / ruleId / properties.cwe），UCSS 自身报告也出 SARIF（report-template.md）。

**双标准去重键**：`cwe + file + startLine ±3 行邻近`。归并规则：

| 情形 | 处理 |
|---|---|
| 宿主与 UCSS 同键各报 | 合并为一条，标 `corroborated-by: [host-tool, ucss]`，等级取高者 |
| UCSS 独有（宿主未报） | 增量发现——M2 并行门禁**只对这部分行使阻断权** |
| 宿主独有 | 宿主口径，UCSS 报告中不重复计数（防看板双计） |
| 结论冲突（宿主 clean + UCSS 报） | 双列呈现 + §6.2 裁决协议 |

SARIF 属性包扩展一律挂 `properties."ucss.*"` / `properties."utss.*"` 命名空间，不占用宿主字段。

### 5.3 用例字段映射（对应 F6 规则 4）

UTSS 12 字段 ↔ 宿主用例模板的通用映射（全表见 `severity_map.json` 的 `testcase_fields` 节）：

| UTSS 字段 | 通用宿主模板常见对应 | 冲突处理 |
|---|---|---|
| 1 用例 ID/标题 | case id / title | 编号规则不同时保留宿主编号，UTSS ID 入附注 |
| 2 所属功能/模块 | module / epic link | 直接映射 |
| 3 关联需求/来源 | requirement link | UTSS 要求可追溯到需求条目/diff/缺陷号——宿主缺失时**必须补**（铁律 3，不可协商项） |
| 4 业务规则（含出处） | （多数模板无） | UTSS 独有，附注列补齐 |
| 5 所属场景 | test type / scenario | 场景四分类（主/备/异/并）映射进宿主枚举 |
| 6 前置条件 | preconditions | 直接映射 |
| 7 前置数据（具体值+准备方式） | test data | 宿主仅有描述性 data 时标注「不满足 UTSS 合格标准」 |
| 8 依赖（真实/mock 及方式） | dependencies | 直接映射 |
| 9 测试步骤（步骤级预期） | steps | UTSS 要求每步带预期——逐步标注 |
| 10 期望结果（可判定断言） | expected result | 直接映射 |
| 11 优先级 P0-P3 | priority | 枚举对齐 |
| 12 设计方法 | （多数模板无） | UTSS 独有，附注列补齐 |

**不可协商项**：字段 3（来源追溯）、9（步骤级预期）、10（可判定断言）缺省 = 用例不合格（S1 准入硬条件）——映射进宿主模板时这三项以 UTSS 标准为准。

### 5.4 流程档位对齐（UTSS 特有）

宿主已有测试流程时按档位嵌入而非替代：

- 宿主为轻量迭代流程 → UTSS B 档（小型裁剪）嵌入既有迭代节奏；
- 宿主已有完整测试管理（如 ISO 29119 企业内化）→ UTSS C/D 档只做**增量贡献**：AI 生成代码针对性测试（references/08，P1-P10 缺陷模式）与 UCSS 扫描报告作为风险输入（Step 1 联动点），这是宿主流程大概率没有的；
- 档位声明写入测试计划（Step 0 产出），裁剪理由可审计。

## 6. 域内权威与冲突裁决

### 6.1 域内权威原则

| 域 | 默认权威 | UCSS/UTSS 进入方式 |
|---|---|---|
| SAST 工具门禁（宿主已装 Semgrep/CodeQL 等） | 宿主 | M0 起步，M2 仅对去重后独有发现阻断 |
| 测试过程与准出（宿主已有测试规范） | 宿主 | 档位嵌入（§5.4），门禁 G0-G3 作为建议指标呈现，M2 起才独立阻断 |
| D4 逻辑推理审计、D5 供应链配置、密钥扫描 | 通常空缺 | **可直接 M2**（增量价值明确，无宿主可扰动） |
| AI 生成代码针对性测试（P1-P10） | 通常空缺 | **可直接 M2** |
| 报告呈现层 | 集成方 | 双标准并列，去重键归并（§5.2） |

### 6.2 结论冲突裁决协议

宿主 clean + UCSS 报（或反向）时：

1. **双列呈现**，不隐藏任何一方；
2. 门禁裁决权归当前域内权威方（M0~M2 阶段即宿主）；
3. **升级路径**：UCSS 侧补齐证据链（D1/D2 污点链、D4 推理链，含行号）后，提交集成方评审——连续 N 次证据成立的独有发现可触发 §7 M3 权威转移评审；
4. UTSS 结论三值化自带证据要求（执行记录/覆盖率数据），冲突同理。

### 6.3 版本协商

SKILL.md frontmatter（YAML）是机器可读清单：`name` / `version` / `standard` / `metadata.standard`。宿主集成时可 pin 版本（如 `code-scan@1.1.0`）；升级 = 整目录替换 + frontmatter 版本 diff 评审（更新纪律见 UCSS 安装指南 §七）。

## 7. 渐进集成模式阶梯（M0 → M3）

**关键工程事实：M0 无需任何新代码**——`ucss_gate.py --summary-only` 现成即观察模式（输出摘要、不做门禁判定、exit 0）。

| 模式 | 定义 | UCSS 行为 | UTSS 行为 | CI 表现 |
|---|---|---|---|---|
| **M0 观察** | 跑但不裁决 | 全流程扫描 + 报告；门禁脚本用 `--summary-only`（exit 0） | 全流程出报告；结论只呈现，不拦准出 | stage 永不失败 |
| **M1 顾问** | finding 以注记呈现 | 报告 + PR comment / 注记，不改门禁 | 报告作为提测附件；门禁 G0-G3 结果列为建议 | stage 永不失败 |
| **M2 并行门禁** | 独立 stage、只对独有发现负责 | 去重后 UCSS 独有 C/H 级 → 本 stage exit 2 | coverage_gate 独立 stage，不达标 exit 2（阈值按档位） | **独立 stage 失败**，不与宿主 stage 复合 |
| **M3 域内主导** | 接管空缺/被让渡域 | 成为目标域唯一门禁 | 目标域唯一准出标准 | 替换原空缺位 |

**升降级条件**：

- M0→M1：观察期 ≥1 个迭代，报告格式被集成方看板接受；
- M1→M2：去重后独有发现 ≥1 条且经人工复核确认为真阳性（建立增量价值证据）；
- M2→M3：连续 4 周独有发现真阳性率 ≥ 宿主标准同期水平（数据支撑，不凭立场）；
- **M2→M0（回退）**：随时，改 stage 命令即回退——先降级观察 1 个迭代再移除，避免门禁突然消失造成质量真空（§10）。

模式声明放集成方自己的 `interop/coexistence_modes.yaml`（模板随卷），stage 命令与之对应。

## 8. CI 共存管道拓扑（三种）

### 拓扑 1：并行 stage（默认推荐）

宿主门禁与 UCSS/UTSS 门禁物理隔离，互不读对方产物，exit code 各自独立：

```yaml
# GitLab CI 示例（同型适用 GitHub Actions / Jenkins）
host_semgrep:            # 宿主既有 stage——一行不改
  script: semgrep --config p/owasp-top-ten --error .

ucss_observe:            # M0：观察期
  script:
    - semgrep --config auto --sarif -o .ucss-report/semgrep.sarif . || true
    - python3 .standards/skills/code-scan/scripts/ucss_gate.py --summary-only .ucss-report/semgrep.sarif

utss_coverage:           # M2：UTSS 覆盖门禁独立 stage
  script:
    - pytest --cov --cov-report=xml
    - python3 .standards/skills/utss/scripts/coverage_gate.py --input coverage.xml --grade C
```

### 拓扑 2：多工具 SARIF 汇聚

各工具 SARIF 统一上传代码扫描平台（GitHub Code Scanning / 自建看板），展示层用 §5.1 映射 + §5.2 去重键归并——门禁仍在各自 stage。

### 拓扑 3：串行复合门禁（进阶，依赖 backlog 工具）

去重后 AND 复合，需 `sarif_dedup.py`（§12 backlog，CLI 已定）：

```
python3 sarif_dedup.py --baseline host.sarif --incremental ucss.sarif \
  --keys cwe,file,line --line-proximity 3 --mode corroboration-mark \
  -o merged.sarif
python3 ucss_gate.py --fail-on critical,high merged.sarif
```

## 9. 自研智能体适配设计（场景 B）

### 9.1 适配契约（五接口）

自研 runtime 只需实现以下五个消费点，即可完整接入姊妹规范（**全部已核验为现状事实**，非规划）：

| 接口 | 形态 | 约束（已核验） |
|---|---|---|
| I1 规范文本 | SKILL.md + references/（Markdown 规则包，frontmatter 为 YAML） | 无框架依赖；可作提示注入，也可结构化解析 |
| I2 工具脚本 | `ucss_gate.py` / `sync_resources.py` / `coverage_gate.py` / `init_test_docs.py` | **Python ≥3.8 纯标准库**（import 清单已核验：argparse/glob/json/sys/os/fnmatch/datetime/hashlib/shutil/subprocess/urllib.request，后两者仅 sync_resources 网络模式）；默认 OFFLINE 零外联；exit code 语义稳定（0=PASS / 2=FAIL 阻断 / 1=参数错误） |
| I3 配置 | CLI 参数 + 唯一环境变量 `UCSS_NETWORK_MODE` | 无隐藏全局配置、无注册表 |
| I4 报告 | SARIF 2.1.0 / Markdown / JSON | 扩展属性挂 `ucss.*` / `utss.*` 命名空间 |
| I5 清单 | SKILL.md frontmatter（name/version/standard） | 版本协商机器可读 |

### 9.2 三级接入

| 级 | 定义 | 成本（设计目标） | 适用 |
|---|---|---|---|
| **L1 工具级** | 不加载规范文本，只在 CI / 工具链直接调脚本 | ≤30 分钟 | 自研智能体已有成熟 prompt 体系，只想借门禁与 SARIF 聚合 |
| **L2 协议级** | SKILL.md 作为技能 / 系统提示注入，智能体按五步法 / Step 0-9 执行 | ≤半天 | 自研 runtime 支持加载 Markdown 规则（大多数智能体框架天然支持） |
| **L3 原生级** | 解析 SKILL.md + references 为自研规则注册表 / 工作流引擎步骤，工具调用原生映射 | 2~3 天 | 自研安全平台 / 测试平台要做深度产品化 |

**L1 步骤**：① `coexist_check.py --skills-dir` 确认无冲突 → ② 拷 scripts/ 任意位置 → ③ CI 加观察 stage（拓扑 1）→ ④ 验收：`ucss_gate.py --summary-only` 对样例 SARIF 输出摘要且 exit 0。

**L2 步骤**：① 同上装前检查 → ② 把 `code-scan/`、`.standards/utss/` 注册进自研技能目录（按其规范改 frontmatter 之外的封装，SKILL.md 本体不改）→ ③ 验收话术：「帮我扫一下这个项目」→ 回复含五步法扫描计划；「按 UTSS 测试」→ 回复含 Step 0-9 与档位声明 → ④ 文件路由表（按需加载）行为抽查：问具体语言 Sink 模式时才读 language-patterns.md。

**L3 步骤**：① 定义规则导入 schema：UCSS D1~D5 域 + SEC-*/DEF-* 编号体系 + 五级/C1-C3 → 自研规则库结构；UTSS Step 0-9 + 铁律 8 + G0-G3 + 档位 A/B/C/D → 工作流引擎步骤表 → ② 工具调用映射：五步法 Step 2 引用 references/toolchain.md 的命令集 → 自研工具白名单 → ③ 对账验收：导入后规则条目数 = SKILL.md 核心原则 + references 章节计数（可对账）；④ 门禁语义保留：exit 2 必须映射为自研平台的「阻断」而非「警告」。

### 9.3 场景走查 A：自研智能体代码扫描（含共存）

自研智能体「CodeBot」已有 Semgrep 门禁。接入：

1. L1 先行：CI 加 `ucss_observe` stage（拓扑 1），跑 1 个迭代——`--summary-only` exit 0，宿主流水线零感知；
2. 对账去重后增量：本迭代 UCSS 独有发现（多为 D4 逻辑推理与 D5 密钥类——Semgrep 规则集未覆盖域，见 §6.1）8 条，人工复核真阳性 6 条；
3. 升 M2：stage 去掉 `--summary-only`，改 `--fail-on critical,high`——**仅该 stage 失败时阻断**，宿主 Semgrep stage 行为一行未改；
4. （可选）L2：SKILL.md 注入 CodeBot 的技能层，使其对话态也能按五步法出报告，CI 态继续用脚本门禁——两态同一套规则源。

### 9.4 场景走查 B：自研智能体测试接入

自研智能体「TestBot」无既有测试标准（空缺域，直接 M2）：

1. L2 注入 `.standards/utss/`；触发「给这个项目做测试」→ TestBot 按 Step 0 判档位 C，出测试计划（G0：测试项 100% 来自 Step 1 清单）；
2. 五件套落位：`tests/qa/` 为空 → 默认落位（§4.3 规则 1）；若宿主已有文档 → 子命名空间协商；
3. 覆盖门禁接入自研平台：`coverage_gate.py --input coverage.xml --grade C` exit 2 → 平台映射为「阻断」；结论三值（PASS / PASS-WITH-RISK / FAIL）透传至平台准出看板；
4. 与 UCSS 联动：上一环节扫描报告作为 Step 1 风险输入（姊妹规范的既有联动点，无需本卷额外实现）。

### 9.5 依赖与运行时基线

- Python ≥3.8，纯标准库（离线环境零 pip 安装）；
- 默认 OFFLINE：不确定网络状态绝不外联（UCSS Step 0 安全默认），适配内网自研平台无额外网络策略要开；
- HOME 写入面仅 `~/.ucss/cache/`（SYNC 模式；纯 OFFLINE 全程只读目标仓库）；
- 磁盘：技能包 <1MB；报告目录 `.ucss-report/` 建议入 `.gitignore`。
