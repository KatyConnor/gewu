# 07 缺陷管理（Defect Management）

缺陷是测试的核心产出物。低质量缺陷单 = 开发无法定位 = 轮次空转。

## 1. 严重级与优先级定义（双维，不得混用）

严重级 = 技术影响（测试定）；优先级 = 修复紧急度（结合业务定，需用户/需求方确认）。

| 严重级 | 定义 | 典型例子 |
|---|---|---|
| S1 致命 | 系统崩溃/数据丢失/资金损失/安全漏洞/主流程完全不可用 | 支付重复扣款；越权访问他人数据；服务启动即崩 |
| S2 严重 | 主要功能错误，无绕行方案 | 订单状态机卡死；导出内容错误 |
| S3 一般 | 次要功能错误，有绕行方案 | 边界条件下列表排序错；提示文案错误 |
| S4 轻微 | 外观/体验问题，几乎不影响使用 | 对齐偏差；日志冗余 |

- 优先级 P0-P3 与严重级独立映射：S4 的 UI 文字错误在发布会前可以是 P0。
- 定级争议：以「影响 × 概率 × 可恢复性」复述并请用户裁决，不僵持。

## 2. 缺陷单字段（模板 → templates/defect-report.md）

必填：ID、标题（现象一句话）、严重级/优先级、环境（版本/commit）、
**复现步骤**（编号步骤 + 实际结果 + 预期结果，可复现是底线，偶发标注概率与采样方式）、
证据（日志片段/截图/最小复现代码）、来源用例 ID。

补充：根因分析（修复时填）、修复版本、回归验证记录（用例 + 结果）。

## 3. 缺陷生命周期

```
新建 → 确认(开发) → 修复中 → 待验证(已修复) → 回归验证 → 关闭
          │                        │
          └─ 拒绝/延期/无法复现      └─ 验证不通过 → 重新打开
```

- **智能体一体的特殊纪律**：自己修的缺陷自己回归验证时，必须**先跑原复现步骤**，
  再跑受影响面回归；禁止「代码看起来改对了」直接关闭。
- 拒绝/延期的缺陷必须有书面理由并获用户确认，进入遗留清单。

## 4. 根因分析（RCA）——S2 严重以上必做

轻量 RCA 三选一：
1. **5Why**：连续追问为什么（最多 5 层）直到可行动根因
2. **缺陷归类**：需求理解错 / 逻辑错 / 边界漏 / 异常路径漏 / 并发 / 资源泄漏 / 集成契约错 / 环境差异
3. **注入点分析**：缺陷在哪一层应被拦住（单测？集成？评审？）→ 补该层防护，不是只修现象

**修复纪律**：修复必须附带「为什么之前没测出来」的答案——把该场景固化为回归用例（Step 9）。

## 5. 缺陷预防（对智能体开发的定向建议）

每轮结束从缺陷归类统计提炼 1-3 条预防项写进测试报告：
- 高发「边界漏」→ 下轮设计用例强制 BVA 三点法
- 高发「异常路径漏」→ 强制检查每个 catch 块与错误分支断言
- 高发「集成契约错」→ 引入契约断言测试（schema 校验）
