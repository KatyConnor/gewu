# 03 测试用例设计方法库（Design Methods）

设计用例时按「先选型、再设计」。禁止拿起键盘就写用例——无方法用例 = 覆盖靠运气。

## 1. 方法选型路由

先判断测试对象的特征，再选方法（可组合，高风险项至少两种交叉）：

| 对象特征 | 首选方法 | 补充 |
|---|---|---|
| 输入有明确取值范围/格式（表单、参数、配置） | 等价类划分 + 边界值分析 | 错误推测 |
| 多条件组合决定行为（权限校验、优惠规则、审批流） | 判定表 | 条件覆盖（白盒校验） |
| 业务流程/用户旅程（下单、退款、审批） | 场景法（主流程 + 备选流 + 异常流） | 状态迁移 |
| 对象有明确状态机（订单、工单、连接、会话） | 状态迁移测试 | 场景法 |
| 参数组合爆炸（兼容性矩阵、特征开关） | 正交试验法/成对组合（pairwise） | — |
| 复杂算法/表达式/安全关键逻辑 | 语句/分支/条件/MC/DC 白盒覆盖 | 变异测试（D 档） |
| 无规格、经验直觉区、老区域换血 | 错误推测 + 探索式 Charter | 缺陷攻击 |

## 2. 黑盒方法要点（附微示例）

### 2.1 等价类划分
- 每个输入域分「有效等价类 + 无效等价类」，每类取 1 代表值。
- 示例：年龄输入 18-65 → 有效 [18-65] 取 30；无效：17、66、非数字、空、超长字符串、负数、浮点。
- **注意**：无效类必须逐个单独测（一条用例只打一个无效类，避免屏蔽效应）。

### 2.2 边界值分析（BVA）
- 缺陷最爱藏在边界。三点法：min、min+、nom、max-、max；有开闭/长度限制再加 off-by-one。
- 示例：字符串长度 1-64 → 测 0、1、2、63、64、65；数组下标、循环次数、分页 size 上限同理。
- **AI 生成代码重点**：`<` 与 `<=` 混淆、`length` 与 `length-1`、差一错误——BVA 命中率高。

### 2.3 判定表
- 列条件桩/动作桩，n 个条件理论 2^n 列，用规则合并裁剪到可测规模（关注无关项合并）。
- 示例：审批流（金额<1k 免审；1k-1w 组长审；>1w 总监审；任意金额 用户已注销=拒绝）
  → 4 规则判定表，每规则一条用例。

### 2.4 场景法
- 从基本流开始，逐个分支挂备选流/异常流，形成场景矩阵。
- 每条场景 = 一条用例，明确前置条件、步骤、预期（含中间状态断言）。
- **必含**：每条基本流至少 1 条异常流（超时、拒绝、中断、重复提交、断网重试）。

### 2.5 状态迁移
- 画出状态机（状态 × 事件 = 迁移），设计用例覆盖：所有状态至少一次、所有迁移至少一次（0-switch）；
  高风险再升 1-switch（两跳路径）。
- 同时测**非法迁移**（如已取消的订单再支付 → 必须拒绝）。

### 2.6 正交/成对组合
- 参数多、组合爆炸（如 浏览器×OS×分辨率×语言）→ pairwise 工具或正交表取代表组合。
- 单一缺陷假设下 pairwise 可大幅压缩用例数，交互缺陷高风险参数对再单独覆盖。

## 3. 白盒方法（结构覆盖，用于自测与核心逻辑）

| 覆盖层级 | 含义 | 强度 |
|---|---|---|
| 语句覆盖 | 每条语句至少执行一次 | 最弱，底线 |
| 分支（判定）覆盖 | 每个判定的真假分支都走过 | 标准要求 |
| 条件覆盖 | 每个原子条件的真假都出现 | 检测复合条件内部 |
| MC/DC | 每个原子条件独立影响判定结果 | 航空/安全关键级，D 档核心逻辑推荐 |

- **智能体操作含义**：写完实现后自查「哪些分支没被任何用例踩过」，针对性补用例；
  用 `scripts/coverage_gate.py` 获取实测覆盖率而不是估计。
- 循环测试：0 次、1 次、多次、最大次数；异常路径（抛错分支）必须有用例——AI 生成代码
  的异常分支常是「写了 try 但 catch 里逻辑错」，见 references/08。

## 4. 经验类方法

### 4.1 错误推测（缺陷攻击清单摘要）
高频命中率清单：空输入/null、超长输入、特殊字符与 emoji、SQL/脚本注入载荷、
并发重复提交、时区与夏令时、闰年 2 月 29、文件编码混用、0/负数/浮点精度、
网络中断重试、服务依赖超时、幂等重放、权限旁路（横向/纵向）、资源耗尽（大文件/深递归）。

### 4.2 探索式 Charter 模板
```
Charter：探索 <目标功能>，使用 <资源/手法>，关注 <质量特性>
时限：约 30 分钟工作量 | 产出：发现的问题清单 + 固化为正式用例
```

## 5. 用例编写字段级标准（v1.1，完备性检查清单）

每条用例写入 tests/qa/test-cases.md（模板 → templates/test-cases.md），以下字段**逐项齐备**，
缺任一项 = 用例不合格，不得进入执行（S1 准入硬条件，铁律 1）：

| # | 字段 | 合格标准 | 不合格反例 |
|---|---|---|---|
| 1 | 用例 ID / 标题 | 唯一 ID；标题 = 对象+动作+预期一句话 | 「测试登录」 |
| 2 | 所属功能/模块 | 对应测试计划的测试项编号，可汇总覆盖核对 | 无归属 |
| 3 | 关联需求 / 来源 | 需求条目 / diff / 风险项 / 缺陷号（铁律 3） | 来源空缺 |
| 4 | **业务规则** | 被验证的规则原文或转述 + 出处（需求 §x / 接口文档） | 只写「按需求」 |
| 5 | **所属场景** | 业务场景/用户旅程定位（主流程/备选流/异常流/并发场景） | 「常规测试」 |
| 6 | 前置条件 | 环境/服务/账号状态，可复现 | 「系统正常」 |
| 7 | **前置数据** | 数据项+具体值+准备方式（SQL/API/seed），汇总即可执行 | 「合法数据」 |
| 8 | **依赖** | 外部接口/服务/配置/凭证，注明真实或 mock 及其方式 | 执行时才发现缺依赖 |
| 9 | 测试步骤 | 编号动作 + **步骤级预期**（失败定位到步） | 「操作后观察」 |
| 10 | 期望结果 | 可判定断言：具体值/状态码/状态变更/副作用 | 「功能正常」 |
| 11 | 优先级 | P0-P3（P0 = 主流程与高风险，冒烟池来源） | 全部同级 |
| 12 | 设计方法 | 标注所选方法（BVA/判定表 R2/...），防无方法用例 | 空缺 |

**用例完备性检查（Case Readiness Check）**——用例集写完、执行开始前强制自查：
1. 字段完整性：抽查或全查上表 12 项（P0 用例必须全查）
2. 功能覆盖：测试计划每个测试项 ≥1 条用例（含边界/异常用例）
3. 数据可执行：汇总所有用例前置数据 → 形成数据准备清单，无「到执行时再想办法」
4. 依赖可满足：所有依赖项确认真实可用或有 mock 方案，否则该用例预标 BLOCKED
5. 断言可判定：期望结果全部能写成机器/人类可判定的具体断言
6. 方法合理性：高风险项（R≥12）至少两种方法交叉
检查结论（通过/整改项）记入 test-cases.md 第 1 节，通过后才允许开跑（EXE 批次启动）。

**自动化建议**：回归必跑的 P0/P1 → 自动化；自动化用例同样受本清单约束（断言可判定、可重复、不依赖顺序）。
