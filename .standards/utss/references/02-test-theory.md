# 02 测试思想与理论（Test Theory）

本章是方法论的地基。每条理论都给出「对智能体的操作含义」——不是为了背理论，
而是防止执行时犯这些已被行业验证过的错误。

## 1. 测试七原则（ISTQB CTFL v4.0 第 1 章）→ 执行红线

| # | 原则 | 智能体执行含义 |
|---|---|---|
| 1 | 测试证明缺陷存在，不能证明缺陷不存在 | 通过 ≠ 无缺陷。报告写「未发现缺陷」，不写「没有缺陷」 |
| 2 | 穷尽测试不可能 | 必须做风险排序，把有限轮次压在最高风险区（RBT） |
| 3 | 缺陷集群（80% 缺陷集中在少数模块） | 历史缺陷多的模块、复杂度高的模块加测；在计划中标注重点区 |
| 4 | 杀虫剂悖论（用例老化失效） | 回归用例库每轮审视：连续多轮全过的区域换角度抽查（变异/错误推测） |
| 5 | 缺陷取决于上下文 | 不同系统（Web 服务/CLI 工具/数据管道）测试重点不同，Step 0 定档时判断 |
| 6 | 无假设测试（Absence-of-errors fallacy） | 系统通过了测试但不符合用户需求 = 失败。用例必须源于需求而非代码实现 |
| 7 | 尽早测试（左移） | 不要等「开发全做完」才测。能跑即冒烟，边开发边自测 |

## 2. 测试分层模型 → 用例分布策略

**测试金字塔**（经典：单元 70% / 集成 20% / 端到端 10%，比例为指导思想非死数）：

- 越底层越快、越稳、越便宜；越上层越真实、越脆、越贵
- **智能体操作含义**：新写代码默认补单元测试；用金字塔比例检查用例分布——
  若发现端到端用例占大头，说明测试结构不健康，优先下沉

**金字塔变体**：
- 微服务/契约优先 → **测试奖杯**：集成/契约测试权重 > 单元（服务边界是风险所在）
- 前端重交互 → 组件测试 + 少量 E2E；数据管道 → 数据质量断言 + 端到端抽样
- 判断依据：**风险在哪一层，权重就在哪一层**（与原则 5 一致）

## 3. 左移与右移

- **左移**：需求评审即开始找问题（可测性审查）、开发自测、静态扫描（UCSS 联动点）。
  UTSS 落点：Step 1 影响面分析时同步审「这段代码可测吗」，不可测本身就是缺陷。
- **右移**：发布后监控、灰度、快速回滚。UTSS 落点：测试报告的残余风险清单必须包含
  「建议上线后监控的指标」，把测不透的部分显式交给右移兜底。

## 4. 验证 vs 确认（Verification vs Validation）

- **验证（Verification）**：是否按规格做对了（Build the thing right）→ 用例对照需求条目
- **确认（Validation）**：是否做了对的事（Build the right thing）→ 场景级用例对照用户目标
- **智能体操作含义**：Step 4 用例覆盖验证；但必须至少有 1-2 条端到端场景用例覆盖确认——
  防止「每个函数都对、整件事做错」的系统性失败（AI 生成代码的高发模式）。

## 5. 基于风险的测试（RBT）——Step 1 的方法论

```
风险 = 失败可能性(P) × 失败影响(I)，各按 1-5 打分，R = P × I
```

P 加分项：复杂度高 / 变更频繁 / 历史缺陷多 / 新人（或 AI）新写代码 / 并发与时序逻辑
I 加分项：涉及资金/数据安全 / 核心业务路径 / 影响用户面广 / 不可恢复操作

- R ≥ 12 高风险：多方法交叉设计用例 + 必须自动化 + 回归必含
- 6 ≤ R < 12 中风险：主方法 + 边界补充
- R < 6 低风险：正向用例 + 错误推测抽查

风险清单是活文档：执行中发现缺陷的模块立即上调风险等级，追加用例。

## 6. 充分性准则（什么时候算「测够了」）

单一指标都不可靠，组合判定（与 references/06 门禁联动）：

1. **覆盖率达标**：语句/分支覆盖到档位阈值（覆盖率是必要条件非充分条件）
2. **风险清偿**：高/中风险项全部有执行结论
3. **缺陷收敛**：最近一轮新发现缺陷显著下降（收敛曲线，见 references/05）
4. **变异存活率**（D 档可选）：对核心逻辑做变异测试，杀死率 ≥ 阈值说明断言有效

## 7. 探索式测试与 scripted 测试的配比

- scripted（脚本化）：可追溯、可回归、可审计 → 主体
- 探索式（基于 Charter 的 session）：发现意外缺陷 → 补充
- **智能体操作含义**：S1 按方法设计用例（scripted）之后，允许为每个高风险模块
  追加 1 条「探索 Charter」（如「用畸形输入攻击导出功能，记录系统反应」），
  探索发现的缺陷 → 反向固化为正式用例进入回归库。

## 8. 心理与职业伦理

- 测试的目标是**暴露问题降低交付风险**，不是「证明代码能跑」。
  智能体既是开发者又是测试者时利益冲突最大 → 铁律 5/8（不伪造、二值化结论）就是为此设计。
- 对自己刚写的代码，默认假设「我漏了什么」，重新以对抗视角设计用例。
