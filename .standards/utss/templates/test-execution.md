# 执行计划与执行记录（Test Execution）——UTSS v1.1 模板

> 定位：templates/test-plan.md 定「策略与范围」（测什么、怎么测、轮次与门禁），
> 本文件定「批次与事实」（哪一批、什么环境、逐条结果）。执行前必须有本文件的执行计划节；
> 执行记录逐批次追加，事实与证据为准，禁止事后补写美化。

```markdown
# 测试执行计划与记录：{项目/迭代名}

## 1. 执行计划

### 1.1 前置确认（执行开跑前逐项勾选）
- [ ] 测试计划（test-plan.md）已批准，档位/裁剪声明明确
- [ ] 用例集（test-cases.md）完备性检查通过（字段无缺省，来源 100% 标注）
- [ ] 前置数据准备方案就绪（用例「前置数据」字段汇总去重后的准备脚本/步骤）
- [ ] 依赖就绪：{外部服务/账号/配置/mock 可用性核对；无法就绪的用例预标 BLOCKED}
- [ ] 环境就绪：{版本 commit、部署形态、账号权限}

### 1.2 批次安排
| 批次 | 轮次 | 范围（用例 ID 集） | 环境/版本 | 数据准备 | 进入条件 | 计划顺序 |
|---|---|---|---|---|---|---|
| EXE-1 | T0 冒烟 | {冒烟池 P0 集合} | {本地/容器 commit} | {最小 seed} | G0 通过 | 1 |
| EXE-2 | S1 功能 | {T1 相关全集} | 同上 | {全量 seed} | EXE-1 通过（G1） | 2 |
| EXE-3 | S2 集成系统 | {集成/契约/非功能} | {测试环境} | {mock 配置} | S1 准出 | 3 |
| EXE-4 | S3 回归 | {修复验证+影响面} | 同 EXE-2 | {同上} | 修复包就绪（G2 前置） | 4 |

### 1.3 执行顺序与策略
- 顺序原则：{冒烟优先 → 高风险/P0 优先 → 阻塞项即时上报不空等}
- 重跑规则：{失败用例修复后的重跑批次归属；影响面关联用例联动重跑}

## 2. 执行记录（每批次一节，执行完立即填写）

### EXE-{n} 执行记录（{日期} {时间区间}，版本 {commit}，执行者：{智能体标识/人}）
| 用例 ID | 结果(通过/失败/阻塞/未执行) | 实际结果（关键数据/现象） | 缺陷 ID | 证据索引 | 备注 |
|---|---|---|---|---|---|
| TC-001 | 通过 | {余额 50000.00，流水 1 条} | — | {log#行/截图} | |
| TC-002 | 失败 | {返回 code=5001} | DEF-003 | {resp.json} | 步骤 2 失败 |
| TC-003 | 阻塞 | {依赖服务 X 不可用} | — | — | 阻塞原因+恢复计划 |

**本批次小结**：
- 统计：{计划 m / 通过 a / 失败 b / 阻塞 c / 未执行 d，通过率 a/(a+b)}
- 暂停/恢复：{是否触发 references/05 第 3 节暂停条件及处置}
- 新发现风险：{未成缺陷但值得记录的观察}

## 3. 执行结果汇总（全部批次完成后填写，供测试报告引用）

| 批次 | 通过率 | 新增缺陷 | 遗留阻塞 | 结论 |
|---|---|---|---|---|
| EXE-1 | {100%} | 0 | 0 | G1 通过 |
| EXE-2 | {x%} | {n} | {m} | {继续/暂停} |

- 全量口径：计划 {N} = 通过 {a} + 失败 {b} + 阻塞 {c} + 未执行 {d}（可审计恒等式）
- 缺陷映射：{DEF-xxx ↔ 失败用例 ID 全对照，与 defect-report.md 一致}
- 数据来源声明：{本表数字来自哪些批次记录节，供门禁评估（references/06）取数}

## 4. 记录纪律（铁律 5/7 在执行环节的落地）

1. 逐条记录在执行当时完成，禁止执行完后凭记忆批量补写
2. 「通过」必须伴随关键断言值（实际结果列不得空）；「失败」必须附缺陷 ID 或说明为何暂不提单
3. 阻塞必须写明：阻塞对象、原因、预计恢复时间、恢复后归属批次
4. 环境版本变更（新提测包）必须新开批次，禁止跨版本混合记录
```
