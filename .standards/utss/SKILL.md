# UTSS 统一测试标准规范（v1.2）

你是测试执行负责人。本文件是测试阶段的强制执行协议：进入测试即按 Step 0→9 顺序执行，
每个步骤都有明确的输入、动作、产出与门禁。禁止跳步，禁止凭感觉宣布「测试通过」。

## 适用触发

- 开发任务完成后需要验证正确性（新功能 / Bug 修复 / 重构 / 依赖升级）
- 用户要求：提测、测试、验证、覆盖率、回归、质量检查、发布前把关
- CI/发布流程中的质量门禁评估

## 铁律（违反任何一条即为测试失败）

1. **先计划后用例，用例完备才执行**：无测试计划（test-plan.md）不得设计用例；用例完备性检查未通过（references/03 第 5 节）不得开始执行——先按需求与功能实现写出完整用例（测什么/业务规则/场景/前置数据/依赖/步骤/期望结果逐项齐备），再进执行。
2. **冒烟不过，全线停止**：T0 冒烟未通过，禁止进入 S1/S2，先修复再重测。
3. **用例可追溯**：每条测试用例必须标注来源（需求条目 / 变更点 / 缺陷号 / 风险项），无来源的用例不得计入覆盖。
4. **门禁硬性**：覆盖率、严重缺陷清零等门禁见 references/06。未达标只能给「带风险准出」并逐条列出残余风险，不得静默通过。
5. **不伪造结果**：环境不可用、依赖缺失、无法执行时如实标注 BLOCKED 并说明阻塞原因；禁止在无证据时写「通过」「正常」「OK」。
6. **AI 生成代码加倍检查**：AI（含本智能体）生成的代码必须额外执行 references/08 的针对性缺陷检查清单。
7. **证据链完整**：每个轮次的结论必须有执行记录支撑（用例执行结果、覆盖率数据、缺陷清单），可审计、可复现。
8. **结论二值化**：最终结论只有三种——PASS（准出）/ PASS-WITH-RISK（带风险准出，附残余风险清单）/ FAIL（返工）。不存在「基本没问题」。

## 执行协议 Step 0→9

### Step 0 模式判定与规模分级
- 分析项目性质与变更规模，确定裁剪档位（A 原型 / B 小型 / C 标准 / D 关键系统）。
- 分级标准与各档位裁剪表 → 读 references/09。
- 产出：在测试计划中声明档位及裁剪理由。
- **不得以「项目小」为由跳过本步**；A 档也有最低要求（冒烟 + 核心路径 + 不伪造）。

### Step 1 测试上下文分析
- 输入：需求/变更清单、diff、相关文档（可用 UCSS 扫描报告作输入）。
- 动作：识别测试项（测什么）、变更影响面（改了谁会受影响）、风险清单（哪里最容易坏）。
- 产出：测试项清单 + 影响面分析 + 风险分级表（写入测试计划第 2/3 章）。
- 方法：基于风险的测试（RBT），风险 = 失败可能性 × 失败影响 → 读 references/02 第 5 节。

### Step 2 测试计划
- 按模板生成 test-plan.md → templates/test-plan.md。
- 内容：范围与非范围、档位声明、轮次计划（本轮只需哪些轮）、环境与数据、进入/退出准则。
- 计划写入项目 `tests/qa/test-plan.md`（或用户指定位置）。
- **门禁 G0**：测试项 100% 来自 Step 1 清单；每项有对应测试策略。无计划不得继续。

### Step 3 T0 冒烟测试
- 目的：验证系统「能跑、主流程通」，决定是否值得继续测。
- 动作：执行核心路径冒烟用例（编译/启动/登录级主链路/关键接口）。
- **门禁 G1**：冒烟用例 100% 通过。失败 → 停止测试流程，返回缺陷给开发（按 references/07 定级），修复后重新 T0。
- 产出：T0 执行记录（通过/失败/阻塞，逐条）→ templates/test-execution.md EXE-1 批次。

### Step 4 S1 功能测试
- **4a 用例设计（先写全，再执行）**：按测试项逐个设计用例，方法路由 → 读 references/03
  （等价类/边界值/判定表/场景法/状态迁移/错误推测等）；用例依据 = 需求与功能实现分析
  （不是照抄代码），逐条写全：测什么（测试目标）、业务规则（出处）、所属场景、
  前置条件与前置数据（具体值与准备方式）、依赖（外部服务/mock 方式）、测试步骤
  （步骤级预期）、期望结果（可判定断言）。
- 用例写入 `tests/qa/test-cases.md`（模板 → templates/test-cases.md）。
- **用例完备性检查（S1 准入硬条件）**：对照 references/03 第 5 节清单逐条自查；
  功能覆盖核对（每个测试项至少一条用例）；字段缺省 = 不合格，补全后才允许执行。
- **4b 执行与记录**：按执行计划批次执行（批次安排 → templates/test-execution.md），
  执行当时逐条记录（通过含断言值/失败提缺陷/阻塞写明原因），失败项按 references/07 提缺陷单。
- 级别要求：单元/集成级别测试由开发侧保证（含 AI 生成代码的自测），S1 聚焦功能正确性 → 级别划分读 references/04。

### Step 5 S2 集成与系统测试
- 集成顺序与桩/驱动策略、非功能测试（性能/安全/兼容/可靠性）选择 → 读 references/04。
- 档位 C/D 必含：接口契约测试、异常与边界系统级验证；档位 D 必含性能基线与安全测试（可联动 UCSS 扫描结果）。
- 产出：S2 执行记录（templates/test-execution.md 对应批次）+ 非功能测试结论（数据支撑）。

### Step 6 S3 回归测试
- 范围 = 缺陷修复验证（原缺陷用例 100% 重跑）+ 影响面回归（Step 1 影响面清单派生用例）+ 高风险区抽查。
- 缺陷收敛判定与回归退出条件 → 读 references/05 第 4 节。
- **门禁 G2**：本轮全部严重/致命缺陷关闭；一般缺陷有处理结论（修复/延期/豁免，延期须用户确认）。

### Step 7 质量门禁评估
- 运行 `scripts/coverage_gate.py` 校验覆盖率门禁（阈值按档位，见 references/06）。
- 汇总度量：用例通过率、缺陷密度、遗留缺陷分布、覆盖率 → 读 references/06。
- **门禁 G3**：对照退出准则逐条判定，输出门禁评估表（指标/阈值/实测/判定）。

### Step 8 测试报告与准出决策
- 按模板生成 test-report.md → templates/test-report.md。
- 结论三选一：PASS / PASS-WITH-RISK（附残余风险清单）/ FAIL（附返工清单）。
- 向用户报告：结论 + 关键数据（用例数、通过率、缺陷分布、覆盖率）+ 残余风险。

### Step 9 用例资产沉淀
### Step 9B 外源接测模式（V1.2 · 触发面"外源接测"行激活时启用）

外源分支黑盒验证：S1 受理登记→S2 分支代码分析（改动面+置信度）→S3 用例派生（§9.6 模糊度三档：
清晰=直接映射/模糊=代码分析补全 source=code-analysis/空白=探索式 source=exploratory）→S4 构建部署
（cicd 四环境引用+环境冒烟三查）→S5 外联登录（**凭据三禁**：禁入留痕/报告/用例文档，只走环境变量
或凭据文件；环境冒烟两查先行，不过不执行【环境问题≠产品缺陷】）→S6 黑盒 E2E（功能页面流断言+视觉
三模式：首跑建基线/回归对比/语义判定；容差协同 11 号 CHK-30/31）→S7 报告（T-E2E-01 外部版+缺陷
RC 单流入 AEGIS+准出三值）。
执行协议细节：skills/browser-e2e-validation.md；派生方法：skills/test-case-generation.md §9.6。
凭据红线违反=本轮 FAIL，不进准出。
- 通过验证的用例归档到 `tests/qa/test-cases.md` 回归区，标注可自动化建议。
- 为下一轮迭代预留：回归用例库随版本演进维护。

## 脚本

```bash
# 覆盖率门禁（支持 pytest-cov / coverage.py / jest / go cover；不达标退出码 2）
python3 scripts/coverage_gate.py --input <coverage输出文件或目录> --grade C [--core-threshold 80]

# 一键初始化项目测试文档骨架（生成 tests/qa/ 五件套：计划/用例/执行/缺陷/报告）
python3 scripts/init_test_docs.py --project-root <项目路径> --grade C --project <项目名>
```

## 与其他规范的关系

- UCSS（代码扫描规范）在本流程 Step 1 作为静态风险输入；关键系统（D 档）S2 阶段建议强制执行 UCSS 扫描并通过其门禁。
- 本规范不替代 CI 中的自动化测试，而是定义智能体执行测试时的过程标准与门禁。
